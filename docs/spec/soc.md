# SoC top, KV260 integration and software images

Status: draft — soc track — 2026-10-13

## 1. `tanager_soc` (simulation top and the FPGA's SoC core)

### Purpose
Assembles the cores and the uncore (plan §3.1):
- `N_CORES` `tg_core` instances;
- `tg_xbar` with the cores' ports;
- the L2 (2 banks), each bank's memory path (latency injector → DRAM window → an AXI4 master port);
- the device bus with ACLINT, PLIC, UART and host control;
- the boot ROM;
- the host bridge.

It is board-independent: the same top runs in Verilator with AXI memory models and inside `kv260_top` with the PS.

### Interface
| Port | Domain | Contents |
|---|---|---|
| `clk`, `rst` | core | the core clock; synchronous SoC reset (MMCM lock and PS reset, synchronised by the board top) |
| `clk2x` | core | twice `clk`, rising with it, for the cores' UltraRAM register files (URF, DR-174); 0 and unused without them |
| `clk_host`, `rst_host` | host | host bridge AXI4-Lite side |
| `s_axil_*` | host | host AXI4-Lite slave ([host.md](host.md)) |
| `host_irq_o` | host | to `pl_ps_irq0` |
| `m_axi_*[N_MEMPORTS]` | core | one AXI4 master per L2 bank: 128-bit data, 40-bit address (already remapped onto the carve-out), 6-bit ID |
| `trace_*` | core | each core's commit-trace ports, passed out for simulation harnesses; inside, `tg_trace_stream` streams them into DDR and drives each core's `trace_stall_i` ([uncore-trace.md](uncore-trace.md)) |
| `m_axi_trace_*` | core | the trace stream's AXI4 write master (AW, W, B; no reads): 128-bit, 40-bit PS physical address, one ID; `S_AXI_HP3_FPD` on the KV260 |
| `status_o` | core | LEDs and debug: reset states, L2 init, UART activity |

### Parameters
| Parameter | Default | Meaning |
|---|---|---|
| `N_CORES` | `NUM_CORES` | 1 for M4 (single agent), 2 from M8 |
| `BOOT_ADDR` | `BOOTROM_BASE` | `boot_addr_i` of every core; bare-metal simulation passes `DRAM_BASE` |
| `CLK_HZ` | 100 000 000 | core clock (ACLINT tick, UART timeout, reported to the host) |
| `L2_SETS`, `L2_MSHR`, `L2_DATA_LAT` | 1024, 24, 2 | [l2.md](l2.md). `kv260_top` passes its own `L2_DATA_LAT` (`build.tcl` `TG_L2_DATA_LAT`), whose default 0 picks 4 above 150 MHz and 2 otherwise; any other value is used as it is (DR-146) |
| `CORE_RST_INIT`, `UNCORE_RST_INIT` | 1, 1 | host `CTRL` reset value; simulation testbenches use 0, 0 |
| `DRAM_BASE_INIT`, `DRAM_SIZE_INIT` | 0, 0 | DRAM window at reset; simulation uses base 0 and the model's size |
| `UNCORE_DSP` | `64'h84_0308_0000`: the sites that met 200 MHz as DSPs (the device bus's A slice, the L2 banks' C slices, the memory ports' W slices) | register slices whose main data register sits in DSP48E2s, one bit per site (`tg_uncore`; [uncore.md](uncore.md), DR-136): bits 31:0 the crossbar's, 41:32 the memory ports' AR, AW, W, R and B, 43:42 the L2 banks' R slices. `build.tcl` takes it from `TG_UNCORE_DSP` |
| `AR_SLICE`, `B_SLICE`, `D_SLICE`, `W_SLICE`, `XBAR_IN_SLICE`, `XBAR_SLICE`, `MEM_SLICE` | 1, 0, 0, 0, `4'b0000`, 0, 0 (DR-186) | `tg_uncore`'s register slices ([uncore.md](uncore.md), [uncore-mem.md](uncore-mem.md); what each costs and buys is in §Reserve levers). `tanager_soc` and `kv260_top` pass them on, so a build or a fit sets them without RTL edits (DR-146); `build.tcl` takes each from `TG_` and its name (`TG_XBAR_IN_SLICE` 0–15). The defaults live in `tg_uncore_pkg`, with `UNCORE_DSP`'s |
| `DEBUG_CNT` | 0 | the board debug counters and the cores' board-debug words (`tg_core` `DBG_WORD`) ([uncore.md](uncore.md) §Board debug counters; `build.tcl` `TG_DEBUG_CNT`) |
| `VIRTIO_WINDOW` | 0 | the forwarded virtio window (§8.1, [host.md](host.md); `build.tcl` `TG_VIRTIO_WINDOW`). Off, the virtio slots answer denied |
| `HOST_DMA` | 0 | the coherent host DMA port, `s_axi_dma_*` (§8.1, [host.md](host.md); `build.tcl` `TG_HOST_DMA`). Off, the port is ignored and its outputs are 0 |
| `CORE_KIND` | `"core"` | `"core"`: `tg_core` (the stub until the core track's RTL lands); `"trafgen"`: `tg_trafgen` traffic generators in the cores' place, for bring-up and timing runs before the core exists (§2.3) |

### Behaviour
- **Resets.** The uncore resets on `rst` or the host's `CTRL[1]`; the cores also reset on `CTRL[0]`. Each unit registers its own copy of the reset (conventions §4).
- **Interrupts.**
  - `irq_mei`, `irq_sei`: PLIC contexts 2h and 2h+1.
  - `irq_mti`, `irq_msi`: ACLINT.
  - `irq_ssi`: tied 0.
  - `mtime_i`: the ACLINT's `mtime_o`.
  - `merr_o`: PLIC sources 16 + h, edge-triggered.
- **Memory ports.** `N_MEMPORTS` = the number of L2 banks (2).

## 2. `kv260_top` and the Vivado flow

### 2.1 Board top
`fpga/kv260/rtl/kv260_top.sv`:
- **PS block design** (generated by Tcl, below).
- **`tg_clkgen`:** one MMCM fed by `pl_clk0` (100 MHz) that produces `clk_core` (`CORE_MHZ`: 100 for M4; DR-145 sets 125 MHz preferred and 100 MHz minimum for v1) and `clk_host` (100 MHz). The VCO is 1200 MHz when `CORE_MHZ` divides it, otherwise the first multiple of 100 MHz in 800–1600 MHz that `CORE_MHZ` divides in eighths (CLKOUT0's fractional divide): 125 MHz is 1000 / 8. A multiple of 100 MHz keeps `clk_host` an integer divide.
  - **With URF** (`TG_URF=1`, DR-174): `clk2x`, twice `clk_core` on CLKOUT2 (VCO / 6 = 200 MHz at 100), from the same VCO at phase 0, so every rising edge of `clk_core` is one of `clk2x`'s. It has a BUFG of its own and goes through `tanager_soc` to each core, for the double-pumped UltraRAM integer register file. It has no reset: the cores use `rst`, of `clk_core`. Without URF, CLKOUT2 drives nothing and `clk2x` is 0.
- **Reset synchronisers:** `pl_resetn0` and MMCM lock into each domain.
- **`tg_axi4_to_axil`:** from `M_AXI_HPM0_FPD` (AXI4, 32-bit data) to the host bridge.
- **`tanager_soc`.**
- **Memory ports:** the SoC's two AXI4 masters drive `S_AXI_HP1_FPD` and `S_AXI_HP2_FPD` (128-bit, clocked by `clk_core`). The commit-trace stream writes through `S_AXI_HP3_FPD` (its read channels are tied off). The 40-bit addresses are zero-extended to the ports' 49.
- **Host DMA:** `M_AXI_HPM1_FPD` (128-bit, clocked by `clk_core`, 2 GiB at `0x5_0000_0000`) goes to the SoC's DMA port when `HOST_DMA` is set, and to `tg_axi_absent` otherwise (§8.1).
- **Fan** (DR-129): pin A12 (`som240_1_c24`, `fan_en_b`, active low) carries the PS timer's PWM, so Linux's `pwm-fan` driver and its thermal zone keep regulating the fan whatever bitstream is loaded.
  - The block design enables TTC<n>'s waveform outputs on EMIO (`PSU__TTC<n>__WAVEOUT__ENABLE`, `__IO = EMIO`, pins `emio_ttc<n>_wave_o[2:0]`), and `kv260_top` drives `fan_en_b` from the right bit, inverted if needed, as Kria's own PL design does.
  - A bitstream loaded at run time does not reconfigure the PS, so the boot configuration already routes the waveform to EMIO; the PL only connects it.
  - **As read from the board:** TTC0 channel 2 (`emio_ttc0_wave_o[2]`), to A12 uninverted. The facts are in `tools/tcl/tg_kv260_fan.tcl`, shared with spike S1 (`TG_FAN_TTC`, `TG_FAN_WAVE`, `TG_FAN_INVERT` override them).
  - On the board, `fancontrol` maps the AMS's temp1 to pwm1, from 15/255 at 35 °C to 255 at 45 °C. The overlay keeps the `pwmfan` node.
- **PMOD console** (`PMOD_UART`; `TG_PMOD_UART=1` in the build): the RISC-V console UART on the PMOD connector, for a USB-UART module (DR-126). The details are in [fpga/kv260/README.md](../../fpga/kv260/README.md).
  - The line runs 8N1 at the 16550's divisor (115 200 baud after OpenSBI), through `tg_uart_phy` ([uncore-periph.md](uncore-periph.md) §UART).
  - The host bridge keeps a copy of the output and can still send input.
  - Off, `pmod_uart_txd` is high-impedance.
  - The pins are PMOD J2 pins 1 and 2, where the board's CH340 USB UART sits (COM5 on the laptop): H12 for TXD (`som240_1_a17`) and B10 for RXD (`som240_1_b20`), as the board session read them.

### 2.2 PS configuration
Block design `tg_ps` in Tcl (`fpga/kv260/tcl/ps_bd.tcl`), board part `xilinx.com:kv260_som:part0:1.4` with the board preset applied (DDR, MIO, clocks), then:
- `M_AXI_HPM0_FPD` enabled, 32-bit, at `0xA000_0000` (64 KiB used), clocked by `clk_host`;
- `S_AXI_HP1_FPD`, `S_AXI_HP2_FPD` and `S_AXI_HP3_FPD` enabled, 128-bit, clocked by `clk_core`; address apertures covering all of DDR (the device-tree overlay sets the three ports' AFI widths);
- `pl_clk0` = 100 MHz; `pl_resetn0`; `pl_ps_irq0[0]` from `host_irq_o`;
- everything else off.

The block design's ports become a wrapper that `kv260_top` instantiates.

### 2.3 Traffic generator (`tg_trafgen`)
A synthesisable stand-in for a core, with the same TileLink ports.
- **On the board:** under host control, through spare host-control registers, it runs a memory test through the L2 and the DDR path:
  - `l1d`: `AcquireBlock`, a data pattern from an address hash, `ReleaseData`, then re-acquire and check;
  - `l1i` and `mmio`: line `Get`s and device reads.
- **In timing runs:** it keeps the uncore's logic from being optimised away while the core is a stub. The build with `tg_core` stubs (`CORE_KIND = "core"`) is the brief's first bitstream target and checks the tie-offs. The `"trafgen"` build is the meaningful timing number for the uncore.

### 2.4 Flow
Non-project Tcl, run only through `tools/vivado_run.sh` (conventions §9):

| Script | Does |
|---|---|
| `fpga/kv260/tcl/build.tcl <cfg> <kind> <mhz> <outdir>` | in-memory project; board part; `ps_bd.tcl`; read RTL through `tools/tcl/tg_files.tcl` (config package, `rtl/rtl.f`, `fpga/kv260/kv260.f`); XDC; `synth_design`; the floorplan (product builds, DR-181); `opt_design`; `place_design`; `phys_opt_design`; `route_design`; reports; bitstream |
| `fpga/kv260/xdc/kv260.xdc` | pin and I/O standard of the fan; clocks come from the PS and MMCM (derived automatically) |
| `fpga/kv260/xdc/timing.xdc` | asynchronous clock groups between `clk_core` and `clk_host` (the host bridge's crossings are XPM macros with their own constraints) |
| `fpga/kv260/xdc/timing_urf.xdc` | URF only (DR-174): `clk2x` stays synchronous with `clk_core`, so every path between them is timed at the real spacing of their edges, 5 ns; it is asynchronous to `clk_host`; `CLOCK_DELAY_GROUP` balances the two BUFGs' trees. The register file's own exceptions (the paths its slot plan gives a full cycle) are the core's: `rtl/core/regfile/tg_urf.xdc`, which `build.tcl` reads with `-ref tg_urf` |

- **Outputs kept:** `timing_summary.rpt`, `utilization.rpt` (hierarchical), `clock_utilization.rpt`, `cdc.rpt`, `drc.rpt`, the primitive-count check (`primitives.rpt`), and `tanager.bit.bin` (bootgen) for the FPGA manager (`xmutil`).
- **Loading under Linux:** a bitstream loaded at run time does not reconfigure the PS. `fpga/kv260/dtbo/tanager.dtso` is the device-tree overlay that sets `pl_clk0`, the fabric-interface widths (`xlnx,afi-fpga`) and a UIO node for the host window. `fpga/kv260/README.md` is the build and bring-up runbook.
- **Deleted after each run:** checkpoints, run directories and logs (conventions §9).
- **Pblocks (DR-181, 10-21):** product builds (kind core, two cores; `TG_FLOORPLAN`) place spikes §8.17's g4_uncore floorplan between synthesis and `opt_design`.
  - **The pblocks:** the two L2 banks in the URAM column, and the crossbar beside them. They are spikes-2's files (`fpga/spikes/tcl/fp/g4_uncore.tcl`, with `fp_lib.tcl`'s helpers and checks), sourced where they are kept.
  - **The result:** hp1f, at 97.2% placed, reached WNS −0.096 ns with them, against −2.098 ns without (spikes §8.18).
  - **Soft:** the pblocks are soft, Vivado 2025.2's default, so the placer may put some of their cells just outside.
  - **A missing cell** the floorplan names stops the build.
  - **The checks** log `FLOORPLAN_OK`, `_WARN` or `_TIGHT` per pblock, before `opt_design` (above 105% or 115% of its LUT sites) and after placement (its own LUTs above 85% or 90%). `summary.txt`'s `floorplan=` line gives both shares and the worst grade. `TIGHT` means spikes-2 resizes that pblock before the next product build.

### 2.5 Release and development builds (DR-177, DR-180)

| Build | What's in it | Used for |
|---|---|---|
| **Release** (DR-180) | `TG_RELEASE=1`: `RELEASE=1` with no latency injectors, no commit trace and no virtio window. The PLIC keeps its S-mode contexts alone, with 1-bit priorities and no TTC1 source. There is no host console. The DMA port has no line counters, and no completion queue without the trace. The host bridge's crossings carry only the fields built. `summary.txt` says `release=1` and `lat_inj=0` | the board's RISC-V-mode product builds (M7 and M8's four-hart build, `h1_build.sh`; RISC-V mode's tree `tanager-kv260-riscv-rel.dtb`); spikes-2's release-form full chips from DR-180 on |
| **DR-177's release form** | No latency injectors (`TG_LAT_INJ=0`) and no commit trace (`TG_COMMIT_TRACE=0`), with everything else as development builds have it | before DR-180: d4r1's and d4r2's packages, spikes §8.18's hu0 and hu1 |
| **Development** | Every block: both injectors (`summary.txt`: `lat_inj=1`, `release=0`), the virtio window and the host console where configured, and the trace when the build is for lockstep | stage C bitstreams (virtio, the host console, `tanager-host --inj-rd`); board lockstep (needs the trace); the latency sweeps at 0, 120 and 250 cycles, with M8's litmus runs on four harts (DR-177's exit) |

- **The release form can't:**
  - inject latency. `CAPS[1]` = 0, and `tanager-host` refuses `--inj-rd`, `--inj-wr` or `--inj-bw` above 0 before it touches the board. `--inj-rd 0` only gets a note.
  - report native read latency: every `INJ_*` register reads 0 ([host.md](host.md)).
  - run board lockstep: with the trace off, `CAPS[3]` = 0.
  - serve virtio (stage C) or give a console through the host. `CAPS[2]` and `CAPS[9]` = 0: its console is the PMOD UART alone, `tanager-host --pty` stops, and its default stdio console becomes none.
  - count the DMA port's lines (`CAPS[10]` = 0) or record its completions (`CAPS[11]` = 0; they serve lockstep, which needs the trace). `HDMA_WR_DROPS` still counts.
  - take a machine-mode external interrupt, or use priorities above 1 ([uncore-periph.md](uncore-periph.md) §PLIC). Nothing in RISC-V mode does: OpenSBI takes no external interrupt, and Linux writes priority 1 alone. Its device trees list each M context as absent (−1, `sw/dts` `RELEASE=1`). A release tree boots a development build too, whose M contexts nothing uses.
  - take TTC1's interrupt (PLIC source 24, D1's test; the A53 and RISC-V mode don't use TTC1).
- **It changes cycles, not function.** An injector stores each read burst whole before it releases it. So without the injectors each DRAM fill reaches the L2 a few cycles sooner, and release builds run memory-bound work slightly faster than development builds. A comparison across the two kinds says so. DR-180's parts change no cycle: the crossings carry the same values, and the other parts are absent or unused.
- **The saving:**
  - **The injectors themselves,** in d4r1's routed build: 1,371 LUTs (368 of them LUTRAM), 556 flip-flops and 4 RAMB36 (their read buffers).
  - **The whole chip, synthesized** (d4r1's configuration on bdf68a1a, `TG_LAT_INJ=1` against `0`): 114,534 → 113,288 LUTs, so 1,246 fewer (878 logic, 368 LUTRAM); 61,072 → 60,150 flip-flops (922, the host bridge's injector registers and their crossings included); 122 → 118 RAMB36.
  - DR-167 estimated 1,293 LUTs and 4 BRAM36. Placement figures come with spikes' release-form chips (§8.18).
  - **DR-180's parts,** synthesized on hu1's recipe (main 7196a0bc with DR-180, b9a7ce10: `TG_RELEASE` unset against `1`; synthesis only, `AreaOptimized_high`):
    - **The whole chip:** 125,174 → 123,391 LUTs, so 1,783 fewer (1,695 logic, 88 LUTRAM); 67,179 → 64,009 flip-flops (3,170 fewer); 6 → 4 RAMB18. The measured list estimated about 1,550 LUTs, 2,700–3,200 flip-flops and 2 RAMB18.
    - **The host bridge:** 1,416 → 528 LUTs, 5,267 → 2,420 flip-flops, 2 → 0 RAMB18. Of that, the virtio window is 274 LUTs and 574 flip-flops. The console FIFOs, the completion queue and the trimmed crossings are the other 614 LUTs, 2,273 flip-flops and both RAMB18.
    - **The PLIC:** 719 → 119 LUTs, 432 → 211 flip-flops.
    - **The device bus:** 902 → 623 LUTs (the virtio slots' device).
    - **The DMA port:** 96 flip-flops (its cycle count and line counters) and 5 LUTs.
    - **The rest:** within noise (the crossbar −102 LUTs, the cores −26, the top level −74).
    - **Still over the device after synthesis** (123,391 LUTs, 105.4%). hu1 lost 5,119 LUTs in `opt_design` on 071de15c (spikes §8.18), so this release chip would come to about 118.3K after it, still about 1% over: an estimate, not a run. DR-180 covers part of hu1's gap, not all of it.
- **Simulation and the tests** keep every block by default. Release forms:
  - DR-177's: `tests/unit/host_bridge` and `tests/unit/soc` (`LAT_INJ=0`, both in `short`), `tests/unit/boot` `LAT_INJ=0`, and `make lint LAT_INJ=0` (lint-all runs it in both views).
  - DR-180's: `tests/unit/periph` `REL=1`, `tests/unit/host_bridge` `REL=1 HDMA=1` and `tests/unit/hdma` `REL=1` (each in `short`); `tests/unit/soc` `RELEASE=1` (trafgen, and tcore with the DMA port and the PS window, in `short`; `ipirace RELEASE=1`); `tests/unit/boot` `linux RELEASE=1` (the serial console alone); `make lint RELEASE=1` (lint-all runs it with `LAT_INJ=0 COMMIT_TRACE=0` in both views); on QEMU, `RELEASE=1 sw/qemu/boot_test.sh 2 2` and `SMP=4 RELEASE=1 IRQS=1 sw/qemu/debian_test.sh`.

## 3. Boot flow and memory layout

Plan §7.2. With `DRAM_BASE` = `0x8000_0000`:

| Address | Contents | Loaded by |
|---|---|---|
| `0x8000_0000` | OpenSBI `fw_jump.bin` (generic platform, `FW_TEXT_START`) | host; in RISC-V mode the A53's `riscv.scr` |
| `0x8020_0000` | OpenSBI's next stage, at the generic platform's `FW_TEXT_START + 0x20_0000` (no build sets `FW_JUMP_ADDR`): Linux's `Image` with the initramfs built in (simulation, stage C), or U-Boot d4 (`payload.bin`, RISC-V mode), which loads Debian's kernel itself | the same |
| `0x8220_0000` | DTB, at the generic platform's `FW_TEXT_START + 0x220_0000` (no build sets `FW_JUMP_FDT_ADDR`); OpenSBI skips its copy when the DTB is already there | the same |

1. Every hart starts in the boot ROM. It sets `a0 = mhartid` and `a1 = DTB_ADDR`, then jumps to `BOOT_ENTRY` (host control; reset values `0x8220_0000` and `0x8000_0000`).
2. OpenSBI picks the cold-boot hart and boots Linux at `0x8020_0000` in S-mode. Linux brings up the other harts through SBI HSM.

The kernel's effective size (the `Image` header's `image_size`) must stay below 32 MiB, or it would overlap the DTB. `sw/build_linux.sh` checks this.

## 4. Device tree

`sw/dts/tanager.dtsi` describes the plan §5.4 map, preprocessed by cpp for:
- cores (1 or 2) and threads per core (1 or 2), and the threads that run (`RUN_THREADS=1`: thread 0 of each core, harts 0 and 2);
- DRAM size;
- whether F and D exist (M4's core may lack them);
- `VIRTIO=1`: the forwarded virtio window's slots (§8.1), for bitstreams built with it;
- the KV260's peripherals and builds (`UART1`, `SD1`, `BOARD_RESET`, `ETH`, `RELEASE`): every switch, with RISC-V mode's values, is in [firmware_switches.md](firmware_switches.md).

The table gives the default tree's nodes; RISC-V mode's trees differ where noted.

|---|---|---|
| `cpus` | `riscv` | `timebase-frequency` = 10 MHz; `riscv,isa-base` / `riscv,isa-extensions`; `mmu-type = riscv,sv39`; a `cpu-map` with SMT threads in the `smt2` build |
| `clint@2000000` | `riscv,clint0` | ACLINT MSWI + MTIMER, CLINT layout |

`sw/dts/Makefile` builds `tanager-kv260.dtb` and `tanager-qemu.dtb` for one configuration.

**PMP regions: whole pages** (10-21, RISC-V mode's memory gap, [soc-d4-modes.md](soc-d4-modes.md)):
- **The rule:** every MMIO node's `reg` starts on a 4 KiB boundary and covers whole 4 KiB pages.
  - OpenSBI makes a PMP region of each device it uses (its console, the reset syscons, the ACLINT, the PLIC), as large as that node's `reg`.
  - Firmware that adds PMP regions of its own keeps to the same rule.
- **The cost of breaking it:** a region smaller than 4 KiB costs every page its cached PMP result. On d4r2 that was −23.6% on a store loop, +10% on `rdtime` and `clock_gettime`, and −12.7% on sysbench memory.
  - Until DR-182 the core cached a 4K page's PMP result only while `tg_csr`'s flag (`pmp_al`) said every 4K page was PMP-homogeneous, so any region smaller than a page cost every page. Since DR-182 the walker checks each leaf page against every region, and such a region costs only its own page's cached result. The rule stays: it costs nothing.
  - A 4-byte reset syscon did it in RISC-V mode's tree. Its whole page fixed it.
- **The check:** `sw/dts/check_pages.py` runs on every tree the Makefile builds, and the build stops on a range that breaks the rule. Nodes whose `reg` has no size (CPUs, MDIO PHYs) are skipped.
- **The core checks each page itself since DR-182**, so the rule now keeps only each MMIO page's own result cached.

`sw/dts/board-trees.sh <dir> [1|2]` builds every tree the board's packages carry:
- stage C's virtio trees, in 1 GiB and 768 MiB;
- the Linux bench's (DR-141);
- RISC-V mode's (D4, D5).

With 1, the stage C and bench trees match today's packages byte for byte (checked against d4r1's). RISC-V mode's tree has changed since 10-21: its reset syscon spans a whole page, so no PMP region is smaller than a page ([soc-d4-modes.md](soc-d4-modes.md), the memory gap). With 2 they are the four-hart trees.

**Four harts (M7, DR-175), ready for step 5c** (soc-2, 10-20):
- **The trees:** `RUN_THREADS=2` lists harts 0–3, each with its own interrupt controller, and both threads of both cores in the `cpu-map`.
  - The CLINT gets four pairs in hart order.
  - The PLIC gets all eight contexts (2h machine, 2h+1 supervisor) where `RUN_THREADS=1` keeps −1 placeholders.
- **OpenSBI needs no change** (until 10-23's hotplug finding: §5, patch set tg1). The board's `fw_jump.bin` (`sw/build_opensbi.sh`, sha256 `b0094d23…`) was checked on QEMU virt:

### 7.1 Unanswered PL reads and the PS's AXI timeout block

A read on `M_AXI_HPM0_FPD` that no PL slave answers never completes, and the A53 hangs until a power cycle. The board session hung the board this way on 2026-10-14 by running `tanager-host` with the default app loaded. `tanager-host` now refuses unless the overlay's node is in the live device tree (`check_overlay`). The PS also has a hardware guard for this, the AXI timeout block (ATB), which is not enabled on this board.

- **What it is:** one ATB per PS-PL master path; it tracks transactions and, on a timeout, answers the PS master itself and raises an interrupt.
  - **Registers:** `FPD_SLCR` at `0xFD61_6000` (AMD's `xfpd_slcr.h`, Vivado 2025.2's embeddedsw).
  - **One bit per path** in each register: bit 0 FPDS (the switch to the SIOU slaves), bit 1 AFIFS0 (`M_AXI_HPM0_FPD`, our host bridge; UG1087, `ERR_ATB_ISR`) and bit 2 AFIFS1 (`M_AXI_HPM1_FPD`).
  - **Register map:** `ERR_ATB_ISR` `+0x00` (sticky, write 1 to clear), `IMR`/`IER`/`IDR` `+0x04`/`+0x08`/`+0x0C`, `ATB_CMDSTORE` `+0x10` (reset 7), `ATB_RESP_EN` `+0x14` (reset 0: **off**), `ATB_RESPTYPE` `+0x18` (reset 7), `ATB_PRESCALE` `+0x20` (enable at bit 16, value in bits 15:0, reset `0x0000_FFFF`: **off**). The LPD has the same block at `0xFF41_6000`.
- **How AMD's proposed Linux driver uses it** (`zynqmp_atb.c`, posted to the kernel lists in May 2025; not in the board's 6.8 kernel):
  - **Sequence:** clear `ATB_RESP_EN`, set `ATB_RESPTYPE` and `ATB_CMDSTORE` to the chosen paths, set `ATB_PRESCALE = 0x10100` (enabled; "based on 100 MHz clock"), clear `ERR_ATB_ISR`, then set `ATB_RESP_EN` and `ERR_ATB_IER`.
  - **Response:** on a timeout the ATB returns SLVERR, which the program sees as a bus fault. The driver logs "atb: Timeout detected".
  - **Its stated limit:** "only a limited number of AXI timeouts can be registered before the bus will eventually stall".
- **Option A: `tanager-host` enables the ATB on AFIFS0 before its first PL access** (the sequence above, for bit 1 only).
  - **Pros:** an unanswered read becomes a bus fault (SIGBUS) instead of a hang. It also covers what the device-tree check cannot: a design that is loaded but does not answer (clock or reset stopped, a wedged bridge).
  - **Cons:**
    - It writes PS configuration registers from user space; a wrong address can disturb the PS.
    - Whether `/dev/mem` may write `FPD_SLCR` on this firmware is unknown (an XPPU can block it).
    - The timeout formula is not in the sources we have, so the prescaler value needs a measurement.
    - The setting outlives the program, and applies to whatever design is in the PL, until reboot.
    - By AMD's own note it absorbs only a few timeouts.
- **Option B: enable it at boot**, through the proposed driver or a systemd unit that writes the same registers.
  - **Pros:** it protects every program and logs every timeout.
  - **Cons:** the driver is not in the board's kernel, and a boot unit changes the board's setup, which is the board session's area.
- **Option C: the device-tree check alone** (what `tanager-host` does now, with the board session's `xmutil` check in `tg.sh`).
  - **Pros:** it touches no PS registers.
  - **Cons:** it does not protect a loaded design that stops answering.
- **Recommendation:** keep C, and try A on the board once, behind an explicit `tanager-host` command rather than by default.
  - **First step:** read the ATB registers (reads of PS registers are safe) and confirm the reset values above.
  - **Then:** enable AFIFS0 only, and read `0xA000_0000` deliberately with the default app loaded. The expected result is a bus error, not a hang.
  - **Needs the user's consent:** if the ATB does not engage, that read hangs the board, and only a power cycle recovers it.
- **Sources:** `xfpd_slcr.h` and `xlpd_slcr.h` (AMD embeddedsw in the Vivado 2025.2 install); UG1087, `ERR_ATB_ISR (FPD_SLCR)`; the `zynqmp_atb` patch series (lwn.net/Articles/1022531, May 2025); a PYNQ forum thread with similar writes but a different prescaler encoding (`0x1020`; it does not report the result).

### 8.1 Stage C: the board's peripherals through the ARM (virtio)

The RISC-V's Linux uses storage, then network and entropy, through virtio-mmio devices whose back-ends run on the A53 (`tanager-host`). Slots: `0x1001_0000`, 4 × 4 KiB (console, block, network, rng), PLIC sources 1–4 (already reserved in the device tree and the device bus).

**Where the virtio-mmio registers live:**

| Option | How | Pros | Cons |
|---|---|---|---|
| **C-a: registers in the uncore** | The virtio-mmio register set per slot in RTL (features, queue select, sizes, addresses, ready, status, interrupt status and ACK, configuration space). The host reads and writes the registers through its window. | Register reads at bus speed. | About 1–2K LUTs for four slots against an uncore already over budget. RTL for every new field or device type. |
| **C-b: a forwarded window** (chosen, DR-147) | RISC-V accesses to a slot become requests in a small queue the A53 serves. Reads wait for the answer; writes are posted. Interrupt status and ACK stay in RTL, so taking an interrupt needs no round trip. | Little RTL: a request FIFO, a response register and the interrupt bits. Every virtio device type is software in `tanager-host`. | A register read waits for the A53, about 10–100 µs. Linux's driver reads registers at probe time; at run time it writes QueueNotify (posted) and handles interrupts locally. The device-bus path must tolerate long stalls (it has no timeout). |

**The forwarded window (C-b).** A device-bus target at `0x1001_0000`–`0x1001_3FFF`, four 4 KiB slots.
- **Accesses:**
  - The control registers are 32-bit.
  - The configuration space also takes 8- and 16-bit accesses (virtio-mmio requires them for narrow fields), so a request carries its size.
- **Forwarded:** every access except two registers of each slot. A queue entry is {slot[1:0], offset[11:0], size[1:0], we, wdata[31:0]}.
  - Writes are posted: the device bus acknowledges once the entry is queued.
  - A read waits in the same queue behind earlier writes, and holds the device-bus response until the host answers (`tg_tl_dev`'s wait input, [uncore.md](uncore.md) §Device bus). The device bus has no timeout.
  - The queue (16 entries, LUTRAM, an asynchronous FIFO into `clk_host`) back-pressures the device bus when full.
  - 64-bit accesses answer denied: virtio-mmio uses 8-, 16- and 32-bit ones.
- **Local:** InterruptStatus (`0x060`) and InterruptACK (`0x064`) of each slot are answered in RTL, so taking an interrupt needs no round trip.
  - Each slot has two status bits: bit 0, used buffer; bit 1, configuration change.
  - The host sets the bits through a register, and the driver's InterruptACK clears them.
  - The bits' OR is the slot's PLIC source, 1–4, level-triggered.
- **Host registers** (host bridge, `clk_host`, `0x1100`–`0x1114`; the layout is in [host.md](host.md)):
  - `VQ_CTRL`: `EN`, the host serves the window;
  - `VQ_STATUS`: the queues' counts, a read waiting, the slots' status bits;
  - `VQ_REQ0`, `VQ_REQ1`: the oldest entry in two words; reading the second pops it;
  - `VQ_RSP`: a write completes the waiting read with its data;
  - `VQ_IRQ`: sets or clears the slots' status bits.
  - `VQ_RSP` and `VQ_IRQ` cross in one 16-entry event queue, so the RISC-V side sees them in the host's order.
  - A host interrupt bit (`IRQ_STATUS[4]`, on `pl_ps_irq0`) is raised while the queue is not empty.
- **Not served** (`EN` = 0, its reset value): the window answers every access itself, reads with 0 and writes by dropping them. Linux's virtio-mmio driver then finds no device (`MagicValue` 0) instead of waiting forever for a host that isn't there, so a device tree can list the slots in every build that has the window.
- **Switch:** `tg_uncore` `VIRTIO_WINDOW` (`TG_VIRTIO_WINDOW=1`; off by default, cycle-identical when off). The slots then answer denied, as before. `CAPS[2]` says which.

**The coherent host DMA port.** Virtqueues and buffers are in RISC-V memory, and the back-end reaches them through this port, so neither side does cache maintenance. `/dev/mem` on the carve-out would read DDR behind the L2's dirty lines, so it can't be used.
- **Path:** `M_AXI_HPM1_FPD` (128-bit, clocked by `clk_core`; 2 GiB at `0x5_0000_0000` in the block design, so AXI address bits [31:0] are the offset into the RISC-V's RAM, below `DRAM_SIZE`), then the AXI4-to-TileLink bridge `tg_hdma` (TL-UH: `Get`, `PutFullData`, `PutPartialData`, one 64-byte line per message), then the crossbar's `hdma` initiator (`tg_xbar` `HOST_DMA`), then the L2.
- **AXI4 rules:** INCR bursts; FIXED and WRAP answer `SLVERR`. One read burst and one write burst at a time, each with one line message in flight, so responses are in order.
  - **A read** takes each line its burst touches with one `Get` and returns the beats in order (a narrow beat carries its 16-byte lane).
  - **A write** gathers each line by byte strobe, then sends it as one `PutFullData` (all 64 bytes written) or `PutPartialData` (with the masks), and takes the next line's beats after the `AccessAck`.
  - Beyond `DRAM_SIZE` nothing is forwarded: a read beat answers `DECERR`, a write beat is dropped.
  - **Writes always answer OKAY.** On the A53 an error on a posted write is an asynchronous SError, which panics its Linux (the Cortex-A53 has no RAS extension); a read's error is a synchronous abort, a SIGBUS to the reader. A write burst not done in full counts in `HDMA_WR_DROPS` ([host.md](host.md)).
- **Without the port** (`HOST_DMA` = 0) the block design still has HPM1, and `kv260_top`'s `tg_axi_absent` answers it: reads with `DECERR`, writes dropped with OKAY. A stray A53 access then fails instead of hanging the ARM.
- **Coherence:**
  - The L2 serves the port coherently. A read sees the cores' dirty lines (the L2 probes the owner first).
  - A write completes, with AXI B, only after the L2's AccessAck, which follows the invalidation of every L1 copy.
- **Lockstep:** with `HDMA_CTRL[0]` set, each written line's `AccessAck` queues a completion, {line, cycle}, in a 16-entry queue the host pops through the host bridge (`HDMA_CPL0`, `HDMA_CPL1`); a write waits while the queue is full. The cycle is the trace records' capture count: `tg_hdma` keeps its own copy, which a simulation assertion checks against the trace stream's. `tanager-host run --trace` hands (address, data, cycle) to `tanager-lockstep` as external-write records, one per store into the RISC-V's RAM. They go between the ring's records in its trace output, each ahead of every record captured after its store (`sw/host/extwrite.c`; [verification.md](verification.md) §3.10; [host.md](host.md)). No DMA data enters the hardware's trace stream.
- **Switch:** `tg_uncore` `HOST_DMA` (`TG_HOST_DMA=1`; off by default, cycle-identical when off). `CAPS[8]` says which.

**Notification and completion.** A QueueNotify write reaches the A53 as a forwarded request. The back-end then works the virtqueue through the DMA port, updates the used ring, and sets the slot's status bit with `VQ_IRQ`. The driver's InterruptACK clears it.

**`tanager-host` back-ends** (a virtio-mmio device model per slot, version 2 registers), in this order:
1. **virtio-blk** on an image file on the A53's filesystem: `tanager-host run --blk <image>`. Later the RISC-V's own SD partition (below).
2. **virtio-net:** a TAP device on the A53, bridged with its Ethernet (`br0`), so the RISC-V gets its own address on the LAN: `tanager-host run --net tanager0 --net-bridge br0` ([host.md](host.md)). The bridge is an A53 OS change: approved in advance (DR-147), set up with an automatic rollback, and logged with its undo in `fpga/kv260/README.md`, as every A53 change of stages C and D is. Debian's image takes its address by DHCP (systemd-networkd), with systemd-resolved and systemd-timesyncd. On the board (sc2, 70 MHz, 2026-10-17): ping to the A53 1.3 ms with 1400-byte frames; a 112 MB `apt-get download` at 1.3 MB/s, with apt's http method at a whole core, so the guest sets the rate, not the back-end (its idle wait in `ppoll` gained 9% over a 200 µs sleep). `apt-get update` moves 85 kB/s: apt's index work at 70 MHz.
   - **At 100 MHz (sc3, board session, 10-17):** the same download back to back, from the frozen bench image, measured 1,811 kB/s against sc2's 1,287 kB/s at 70 MHz. That is 1.41×, the clock ratio.
     - **CPU-bound at both clocks:** user plus system time is 96–97% of the wall time.
     - **TCP is clean at both clocks:** no retransmits, timeouts or out-of-order or receive-queue drops (nstat), and no packets dropped by eth0, the A53's TAP or the bridge.
     - **GRO** merges 7–10 wire segments per batch.
     - **The earlier slow runs:** two at 100 MHz moved about 630 kB/s, with apt using the same CPU time spread over three times as long. So packets were arriving slower: the internet path or the mirror at that time, not the core or the virtio device (`fpga/kv260/board/sc3`, "TCP look").
3. **virtio-rng:** from the A53's `getrandom()`.

The console stays the 16550 UART (PMOD, with the host's copy). Debian's kernel has no SBI console tty, so the console must be a UART.

1. The image file on `p2` first. It needs no repartitioning.

- **The check:** a 64 MiB file written with fsync survived the power-off and verified on the next boot, and `e2fsck -fn` on the A53 was clean.
- **The A53's cloud-init regrew its root:** Ubuntu's `growpart` and `resizefs` modules run at every boot ("frequency always"), and they took the freed space back 16 s into the boot after the first shrink. A `/etc/cloud/cloud.cfg.d` file now turns both off. Any A53 image that gives card space away needs the same.

A bigger cloned card is the alternative if the user prefers it. The board session does the work on the board, and the A53's Ubuntu stays intact and bootable.

**Tests** (with the verification track):
- **The window** (done): `tests/unit/host_bridge` `VIRTIO=1` serves the queue from a host model with random delays (one read waits 100K host cycles), checks posted writes in order, a full queue holding the device bus, and the status bits. `tests/unit/periph` `VIRTIO=1` checks the device bus's wait with a stub that answers garbage until it stops waiting. `tests/unit/soc` `VIRTIO=1`: the RISC-V program reads through the window and takes a slot's interrupt through the PLIC.
- **The DMA port** (done): `tests/unit/hdma` runs `tg_hdma` between an AXI4 master and a TileLink memory model (random bursts, narrow and unaligned beats, partial strobes, denied lines, the window's end, FIXED and WRAP, a read and a write at once, completions). `tests/unit/soc` `HOST_DMA=1`: the host reads a buffer the program left dirty in its cache and writes one it holds copies of; the program then reads the host's bytes. `tests/unit/host_bridge` `HDMA=1` checks the completion registers.
- **Lockstep with DMA:** the checker learns each external write and its AccessAck cycle, from DPI in simulation and from the completion FIFO on the board.

**Order of work:**
1. Phase 0 and 1: the two-core platform bitstream, and two-hart Linux on the board.
2. The window and the DMA port, as RTL with host registers, each switchable and off by default, with their tests.
3. virtio-blk, U-Boot and the Debian image: Debian 13 boots from the image file.
4. virtio-net (bridged), then virtio-rng.
5. The RISC-V's own SD partition.

### 8.2 Stage D: dual boot, the RISC-V drives the PS's peripherals

After the A53 boots it hands the board to the RISC-V and parks. The RISC-V's own drivers then run the PS's SD, GEM Ethernet, USB and UART controllers. Each OS has its own SD partition.

**The PL-to-PS path.**
- An uncore target window (a device region of the RISC-V map) with an AXI4-Lite master into `S_AXI_LPD` reaches the IOP peripherals' registers (`0xFF00_0000`–`0xFFFF_FFFF`).
- **Confirmed in the PS IP's own address map** (Vivado 2025.2, `zynq_ultra_ps_e` v3.5, memory map `SAXIGP6`; 10-17):
  - by default `S_AXI_LPD` reaches the lower LPS slaves, `0xFF00_0000`–`0xFFFF_FFFF`, as one 16 MiB block (`LPD_LPS_OCM`). That block holds the IOP (UART0/1 `0xFF00/0xFF01_0000`, GPIO `0xFF0A_0000`, GEM3 `0xFF0E_0000`, TTC1 `0xFF12_0000`, SD1 `0xFF17_0000`, IOU_SLCR `0xFF18_0000`), USB0's glue registers (`0xFF9D_0000`) and the LPD DMA (`0xFFA8_0000`);
  - with `PSU__EXPAND__UPPER_LPS_SLAVES` = 1 it also reaches the upper LPS slaves, `0xFE00_0000`–`0xFEFF_FFFF`, which hold USB0's DWC3 core at `0xFE20_0000`;
  - the port's address is 49 bits wide and its ID 6 bits.
- Device accesses are at most 8 bytes, so AXI4-Lite suffices.
- The XPPU must allow that master to reach these peripherals.

**Interrupts.** The PS routes the four peripherals' interrupts to the PL (the PS-to-PL interrupt signals, enabled in the PS configuration). They go to free PLIC sources, for example 20–27.
- The signals, from the same IP: `ps_pl_irq_uart1`, `ps_pl_irq_sdio1`, `ps_pl_irq_enet3`, and `ps_pl_irq_usb3_0_endpoint[0]` (the DWC3 host line of `[3:0]`). Each is enabled by its `PSU__IRQ_P2F_<NAME>__INT` parameter (`UART1`, `SDIO1`, `ENT3`, `USB3_ENDPOINT__INT0`).
- D1's test uses `ps_pl_irq_ttc1_0` (`PSU__IRQ_P2F_TTC1__INT0`). `ps_pl_irq_adma_chan[7:0]` is there too.

**Peripheral DMA.**
- The SD, GEM and USB controllers are bus masters that write DDR through the PS interconnect, behind the RISC-V's L2.
- **Addresses** are a device-tree matter: `dma-ranges` maps RISC-V RAM (`0x8000_0000`) to the PS bus address the controllers must use.
- **Coherence** with the L2 has three options:

| Option | How | Pros | Cons |
|---|---|---|---|
| **D-a: cache maintenance** | Zicbom in the core (`cbo.clean`/`cbo.inval`) and flush and invalidate by address in the L2. Linux's non-coherent DMA operations then work (`riscv,cbom-block-size`). | Standard. No copies. Direct DDR bandwidth. | RTL in the core and the L2 (Zicbo* is planned for M9), so stage D waits for it. Maintenance costs CPU time per buffer. |
| **D-b: bounce buffers** | An uncached alias of part of the carve-out: a PMA region the L2 does not cache, routed straight to the memory port. Linux's `restricted-dma-pool` (swiotlb) bounces all peripheral DMA through it. | No core changes; ready for M5. | Every DMA buffer is copied once. The pool's size limits the I/O in flight. A small uncore change: an uncached route in the crossbar. |
| **D-c: DMA through the PL into the L2** | `dma-ranges` points the controllers at a PS bus address inside an HPM window (PS to PL), which the host bridge forwards into the coherent host DMA port of §8.1. The controllers' DMA then reaches the L2 like the A53's back-end does. | Coherent, with no core changes and no copies. Reuses stage C's DMA path. | DMA bandwidth is that of the HPM port and the L2's `hdma` initiator, enough for SD, USB 2 and 1 GbE but not for USB 3 at full speed. Longer latency. The HPM window is shared with the host window (decoded by address). **To confirm** in the ZynqMP TRM and on the board: that these IOU masters can target an HPM window at all. |

  Decided (DR-147): D-c. Debian's kernel drives no non-coherent DMA device without Zicbom, so D-b, whose uncached pool needs a core PMA change, and D-a wait. D-a becomes possible when Zicbom lands (M9).

**The handover sequence** (what the A53 leaves configured):
1. **Boot:** the PMU firmware and FSBL set up the PLLs, MIO pins, resets and DDR. ATF, U-Boot and the A53's Linux follow.
2. **Prepare:** `tanager-host` loads the bitstream and the RISC-V images. The RISC-V device tree describes the peripherals it will own.
3. **Release the devices:**
   - The A53 unbinds its drivers for those controllers and keeps their clocks and resets as they are (`clk_ignore_unused`, or held clock references).
   - The A53 can't keep its root filesystem on the SD card it gives away. It runs from an initramfs, or unmounts the SD first.
   - The SD tap delays, which the A53's driver sets through firmware calls, stay programmed in the IOU registers.
4. **Open the protections:**
   - The SMMU passes the controllers' stream IDs through, or maps them as an identity.
   - The XMPU lets their DMA reach the carve-out (or the HPM window for D-c).
   - The XPPU lets `S_AXI_LPD` reach their registers.
   - This may need a custom PMU-firmware isolation configuration.
5. **Park:** the secondary A53 cores go off (PSCI `CPU_OFF`). The boot core waits in a WFI loop. The PMU firmware keeps running (power management, watchdog).
6. **Release the RISC-V** (core reset off). Its Linux probes the controllers.

**The RISC-V device tree.**
- The controllers' nodes list ZynqMP's compatible first, for the drivers' ZynqMP quirks, and the generic one after: `xlnx,zynqmp-8.9a` and `arasan,sdhci-8.9a`, `xlnx,zynqmp-gem` and `cdns,gem`, `xlnx,zynqmp-uart` and `cdns,uart-r1p12` (USB0's `snps,dwc3` waits for D6). Nothing in them calls the PMU firmware (EEMI through ARM SMC, which the RISC-V doesn't have): the clocks are fixed, and SD1's node has no `#clock-cells`, so its driver takes the ZynqMP quirks without the firmware's tap-delay calls (the plan here had been the generic compatibles alone).
- **Clocks** are `fixed-clock` nodes at the rates the A53 left.
- **Interrupts** go through the PLIC; **DMA** uses the `dma-ranges` above.

**Risks:**
- drivers that assume the ZynqMP firmware for resets, tap delays or PHY setup;
- the PMU firmware's default isolation;
- the PS-to-PL interrupt routing for USB;
- the A53's Linux re-gating clocks it thinks are unused.

Each is checked on the board in stage D's first step, with the UART: the simplest controller, no DMA.

**The fan in stage D** (DR-129). With the A53 parked, its Linux no longer regulates the fan: the TTC keeps its last duty cycle. Options:

| Option | How | Pros | Cons |
|---|---|---|---|
| **F-a: PL controller** | A small controller reads the PL SYSMON's die temperature (SYSMONE4, DRP) and sets the PWM from a fixed curve. | Works without any OS, and keeps working if software hangs. | RTL (an estimated 200 LUTs plus the SYSMON primitive). A fixed curve. Our own thermal policy to get right. |
| **F-b: RISC-V Linux** | The RISC-V's Linux drives the same TTC (the `pwm-cadence` driver over the PL-to-PS port) with `pwm-fan` and a thermal zone reading the PS's AMS or the PL SYSMON. | The same regulation as on the A53, in software. | Depends on the RISC-V's Linux running. If it hangs, the fan stays at the last duty, possibly low. Needs the TTC and a temperature sensor in the RISC-V's device tree. |
| **F-c: both** | F-b regulates, and a minimal F-a acts as a floor: full speed above a temperature threshold, else the TTC's PWM passes through. | Normal regulation from Linux, and safety if either OS hangs. It also protects stage B, should the A53's Linux stop. | Both pieces exist: a comparator and a multiplexer on top of SYSMON in the PL, plus the RISC-V's drivers. |

**Chosen (DR-147): F-a as a full regulator** that keeps the A53's control while it is there.
- **Duty:** the PL drives `fan_en_b` with its own 25 kHz PWM. Its duty is the larger of two:
  - a fixed curve of the PL SYSMON's die temperature (SYSMONE4 over DRP, piecewise-linear with hysteresis, full speed above a top threshold);
  - the A53's TTC duty, which the PL measures from `emio_ttc0_wave_o[2]`.
- **Stages B and C:** the A53's `fancontrol` stays in charge whenever it asks for more than the curve. DR-129 holds: the TTC waveform still reaches the fan.
- **Stage D, or if any OS hangs:** the curve regulates alone.
- **Why not F-b or F-c:** Debian's kernel has no `pwm-fan`, no TTC PWM driver and no temperature driver for this chip. So the RISC-V's Linux would need two or three of our own modules before it could regulate, and the fan would still depend on that Linux running. With F-a the fan never depends on the RISC-V's software, and no new driver is needed.
- **Monitoring:** a read-only register (temperature, duty, source) can be added later for a small driver.
- **Clean room:** no SiFive-compatible PWM is needed. If one is ever added, it is built only from SiFive's published register manual (DR-138).

**D2's sensor: the PL SYSMON, as DR-147** (the coordinator asked first whether it can be read without disturbing the A53's own fan and temperature readings; the board's read-only probes, 10-17, `fpga/kv260/board/d2`). It can:
- **`fancontrol` follows the PS SYSMON, not the PL's.** Its `temp1` is the AMS hwmon's first channel, the AMS's channel 7.
  - The PS SYSMON's temperature register (`0xFFA5_0800`) read `0x9DBC`, 33.6 °C, with `temp1` at 33.5–33.6 °C.
  - The PL SYSMON's (`0xFFA5_0C00`) read `0x9D3E`, 32.6 °C, which is `temp3`.
  - Both convert with T = code × 509.314 / 2^16 − 280.23 °C, the AMS driver's scale.
- **A bitstream load already leaves the PL SYSMON at its configuration defaults.**
  - At boot the A53's AMS driver puts both SYSMONs in the default sequencer mode, disables every alarm and masks the AMS interrupt.
  - After sc3's load, the PS SYSMON still shows the driver's settings (register 41h = `0x2F0F`). The PL SYSMON's configuration and sequence registers (40h–44h, the sequence words) all read 0, while its temperature reads normally.
  - A SYSMONE4 instance whose INIT attributes are all zero keeps exactly that state. The board's reload in part 3, when the next bitstream goes on, confirms the reset at load.
- **So the regulator instantiates SYSMONE4** with every INIT attribute zero and reads register 00h (the die temperature) over DRP, and the A53's `fancontrol` is untouched. The expectation that the A53 would see the same PL SYSMON as today was wrong: with the instance in the fabric the AMS reads it as 0 (the board's d2 result, below). The A53 reads the PL channel only on demand (`fancontrol` reads the PS's), and a DRP read that never answers counts as hot.
- **The alternative** (soc-2's earlier proposal: the PS SYSMON's temperature through `S_AXI_LPD`) is not needed. It remains a fallback.
- **The curve's sensor:** the PL die runs about 1 °C below the PS's LPD sensor (32.6 against 33.6 °C), so `fancontrol`'s curve on the PL temperature sits 1 °C later. While the A53's `fancontrol` runs, the larger duty, its own, rules.

**The rest of D2, as DR-147:**
- **Placement:** `tg_fan` in `kv260_top`, in every board build (DR-150), on `clk_core` with the PL's reset, independent of the uncore's and cores' resets. `TG_FAN_PL=0` builds today's passthrough instead, as a fallback.
- **The PWM:** 25 kHz on `fan_en_b` (active low). Its duty is the larger of the curve's and the A53's TTC duty.
  - **The curve** is `fancontrol`'s as configured on the board: 15/255 at or below 35 °C, then linear to 255/255 at 45 °C, full above, with 1 °C of hysteresis on the way down.
  - **The TTC duty** is the low time of `emio_ttc0_wave_o[2]` per 40 µs period; a constant level counts as 0 or 100%.
- **Status for the board:** a read-only word through the host bridge (temperature code, the curve's duty, the TTC's duty, the output duty), read by `tanager-host fan`. This is a small host-bridge interface addition.
- **Tests:**
  - a unit test against an AXI model of the AMS register (temperatures, an error, a silent read) and a TTC waveform generator;
  - on the board: with `fancontrol` running nothing changes at the board's 31–35 °C; with it stopped (pwm1 = 0) the fan keeps the curve's duty; the status word follows a stress run's heat.

**D2 built (10-17):**
- **The regulator:** `fpga/kv260/rtl/tg_fan.sv`, in `kv260_top` on `clk_core` with `rst_core` (the PL's reset and the MMCM's lock), in every board build. `TG_FAN_PL=0` builds today's passthrough.
- **The temperature:** SYSMONE4 with every INIT attribute zero, register 00h read over DRP every 2^20 cycles (10.5 ms).
- **The duty:**
  - The curve takes fancontrol's thresholds as codes: 35 °C is code 40,562, 45 °C is 41,849, and 1 °C is 129 codes. The slope is 191/1,024 of a step per code.
  - The A53's duty is its low time over 2^18 cycles (2.6 ms, about 65 of its periods, so the window's edges move it by about 2/256).
  - The PWM has 256 steps of 16 cycles: 24.4 kHz at 100 MHz.
- **Full speed** before the first reading, during the PL's reset, and after a DRP read without an answer (2^16 cycles).
- **The status word** reaches the host bridge as `FAN` (`0x1400`; `board_status_i` through `tanager_soc` and `tg_uncore`, 0 elsewhere), and `tanager-host fan` decodes it.
- **Tests:**
  - **`tests/unit/fan`,** against a SYSMONE4 stand-in and an A53 PWM generator. It checks full speed before the first reading; 15/255 at 30 °C; 134 at 40 °C, kept at 39.4 °C (the hysteresis); 111 at 38 °C (the curve 1 °C above); 255 at 46 °C; the A53's 50% and 10% (127 and 25) and its held-low and held-high PWM; and full speed while the DRP is silent. Every duty is checked against the status word and against `fan_en_b`'s low time.
  - **`tests/unit/host_bridge`** reads `FAN` across the status crossing, and `tests/unit/soc` reads it through the SoC.
- **The board build** (`d2_100`, 10-17) is d1's configuration with the regulator, on main 646722b: MR6, and DR-156's four L1D misses in flight by default (the coordinator: the board measures them too).
  - **Timing:** WNS +0.505 ns, WHS +0.010 ns at 100 MHz, with DR-160's 1.0 ns margin during placement and routing.
  - **Area:** 112,446 LUTs placed (96.01%), 1,466 more than d1. The regulator is 119 LUTs, 125 flip-flops, one DSP and the SYSMONE4; DR-156 is the rest.
  - **DR-156's board confirmation:** DR-141's workload set on this bitstream, compared against sc3's three boots (one miss, the same two smt2 cores at 100 MHz). Between sc3's tree (5172c6a) and this one, only DR-156 changes the cores' cycles. The rest is off by default, proven the same function, or the idle PS window.
  - **The board's steps** (package `d2-smt2-c2-100`):
    - the regulator with `fancontrol` running;

- **On the board, steps 0–2** (10-17, the board session):
  - **The regulator works.** PL die 33.9–34.4 °C, against 34.0 °C through the AMS on sc3 a minute before. The duty was 15 throughout. The A53's PWM read 14–15 against pwm1 15. No new dmesg line.

With the D2 regulator loaded, the A53's PL temperature channel reads invalid; the PS channel and `fancontrol` are unaffected. This is in the A53 OS change log (`fpga/kv260/README.md`). Losing the A53's view of the PL temperature costs only monitoring, since `fancontrol` regulates on `temp1` and in stage D the A53 parks.

**Stage C against stage D.** C needs only the host DMA port and a little RTL, and the A53 does the I/O. D gives the RISC-V the whole board at native speed. Its costs are the PL-to-PS bridge, the interrupt routing, DMA coherence, the handover and firmware-free drivers. C stays useful after D, as a fallback and for devices the RISC-V can't drive.

**Stage D's DMA must be coherent** (the verification track's kernel check). Debian's kernel handles a non-coherent DMA device only with Zicbom or T-Head's cache operations, and Tanager has neither. So D-c, DMA through the PL into the L2, is required, not just preferred.

**Stage D's drivers.** Debian's kernel has MACB, PHYLIB and DP83867, as modules. It lacks `sdhci-of-arasan`, `dwc3`, `xilinx_uartps`, any TTC PWM, `pwm-fan` and the AMS driver. Those are our own modules, using generic compatibles and no ZynqMP firmware calls. The fan needs none: the PL regulates it (below).
- **Checked in the image's kernel** (6.12.111+deb13-riscv64, 10-17): `MMC_SDHCI_OF_ARASAN`, `USB_DWC3` and `SERIAL_XILINX_PS_UART` are not set. `MMC_SDHCI`, `MMC_SDHCI_PLTFM`, `USB_XHCI_PLATFORM`, `MACB` and `DP83867_PHY` are modules. The ZynqMP-only options (`GPIO_ZYNQ`, `PWM_CADENCE`, `ZYNQMP_FIRMWARE`) don't exist on riscv64.
- `DMA_RESTRICTED_POOL` is not set either, so D-b would need a kernel of our own as well as its PMA change. That leaves D-c as the only option with Debian's kernel until Zicbom (`RISCV_ISA_ZICBOM` is built, but the core lacks the extension).

**Order of work** (soc-2's plan, 10-17, DR-153: M5 runs alongside the core tracks' M6). Cheap board probes come first, because one answer can change D-c. Next comes the PL-to-PS path, tried on the simplest controller with no handover. Then come the steps that need the A53 off the card, in order of value: the root file system, the network, USB. The board session runs the board steps.

- **D0: probes on sc3, before any new RTL.** sc3's host DMA port is already D-c's path.
  1. **Can a PS master other than the A53 write through HPM1?** An LPD DMA channel (ADMA, an LPD master like the IOU's GEM, SD and USB) copies a buffer from the A53's memory to `0x5_0000_0000` + o. `tanager-host dma read` must then show it, and a RISC-V program that held the line in its cache must read the new bytes.
     - If it fails, which block refused (SMMU, XMPU or the address decode) decides what follows.
     - If IOU masters cannot reach HPM1 at all, D-c falls, and stage D waits for Zicbom (D-a, M9): Debian's kernel has no restricted pool for D-b.
  2. **What the A53's boot leaves:**
     - the SMMU's state: the `arm-smmu` bypass setting, and which streams it attaches;
     - whether the XPPU and the XMPUs are enabled;
     - the clock rates of UART1, SD1, GEM3 and USB0 (`clk_summary`).
  3. **The board's wiring:**
     - the DP83867's MDIO address and its reset;
     - the USB5744 hub's reset;
     - which controller the micro-SD is on (SD1);
     - whether the SOM's eMMC is fitted. If it is, the A53 can keep its root there and hand over the whole card.
  4. **Done (soc-2, 10-17):** `S_AXI_LPD` reaches the IOP's and USB's registers, and the four controllers' PS-to-PL interrupt signals exist (the PS IP's address map and ports, above).
  - **The tools:** `tanager-host dma adma` (item 1) and `tanager-host psrd` (item 2's register reads), with the procedure in the board package `d0-probes-20261017` ([host.md](host.md)).
  - **The coordinator's conditions** (10-17): sc3 loaded; read-only on PS state, except the ADMA copies, which stay inside the RISC-V's carve-out; the fan stays with the A53's `fancontrol`. The results come before D1's RTL is final.
  - **Done on the board** (the board session, 10-17, `fpga/kv260/board/d0`):
    - **D-c stands:** ADMA channel 8 copied 4 KiB DDR → HPM1 → DDR, both ways ok, 0 words wrong. The host DMA port's line counters moved by exactly the ADMA's 64 lines each way. The cores were held, so the RISC-V's cache side wasn't exercised. It is the same port and L2 path whose coherence stage C's virtio already relies on.
    - **The SMMU is disabled** in the live tree (`iommu@fd800000`), so no PS master is translated.
    - **`S_AXI_LPD`'s AFI** (FM6) is out of reset (`RST_LPD_TOP` bit 19 clear) at its reset width, 128 bits (`RDCTRL`/`WRCTRL` = `0x3B0`), which D1's port uses.

  - **The window** (`TG_PS_WINDOW`, off by default and cycle-identical when off):

    - an AXI4-Lite master into `S_AXI_LPD`, on `clk_core`;

      - **`tests/unit/periph`'s directed sequences** follow the coordinator's list:
        - a complete where the source is disabled;
        - an enable or a priority written while claimed;
        - completes from other contexts;
        - an affinity move.

        `tg_plic` follows the spec in each, and Linux 6.12.113's EOI recovers each, except the race it leaves: an affinity move between its enable read and its complete. That race freezes the source, as the spec says.
      - **The mechanism, found (10-20, after the board's capture):** a race in the core. The capture (boot 54's shutdown) showed source 21 claimed and never completed, and the probe's complete brought it back.
        - **The race:** the ROB takes an interrupt when `irq_take && !mmio_busy`. The LSU issues the head's MMIO load (`mm_go`) checking only the registered flush, and `mmio_busy` rises only the next cycle, when the port leaves `X_IDLE`. So in one cycle the ROB can take an interrupt while the LSU issues the head's MMIO load.
        - **What follows:** the request is already out (`X_REQ`; a valid can't be withdrawn), so it reaches the device. The flush the next cycle marks it killed, and its response is dropped. After the trap the load runs again. A device read with a side effect happens twice.
        - **For Linux's PLIC claim:** `plic_handle_irq` runs in S-mode with interrupts off, so only M-mode interrupts can land there, OpenSBI's IPIs above all. The first claim takes source 21 and its ID is dropped. The second returns 0, so Linux never handles or completes 21.
        - **Why only at transitions:** IPIs are frequent at boot and shutdown (TLB shootdowns, reschedules) and rare under the pinned read stress.
        - **The directed test:** `make -C tests/unit/soc ipirace` (`tb_soc` `+ipi_race=N`). It sets hart 0's MSIP mid-cycle in the very cycle its LSU issues claim number N, in the ACLINT's register and in its output register; the output to the hart's interrupt selection is combinational, so it is taken that cycle.

          On today's RTL the PLIC claims 21, hart 0 drops that response as a killed MMIO load, the reissued claim returns 0, and the source stays claimed with its line high: the board's state. It passes once the core issues no MMIO load in a cycle where it takes an interrupt (the core track's fix).

### 8.5 DDR write streaming and the L2's write-back batching (10-23)

- **On the board:**
  - u100 (MR35): memgap's wr16m streams DDR writes at 156.3 MiB/s against d4r2's 182.4 (−14%), while rd16m reads 13.5% faster. The DR-141 set's page-fault test, the kernel clearing 2 MiB huge pages, is 8.8% slower.
  - rc2's two slower store rows (board MR37: memset 1 MiB +9.3%, page fault +4.7%) were one unpinned run each. Pinned, rc2 matches u100 within 1% over 16 and 22 sets (MR38), and in tb_boot the four trees from u100's RTL to rc3's run the same store loops to the cycle.
  - memcal, bare metal (MR38): u100's memset-16M runs 159.1 MiB/s against d4r2's 188.3 (18.4% more cycles; d4r1's 161.5). Every other row is faster on u100: reads −22%, the chase −19%, the copies −5%.
  - Two cores write 2.07× one core's rate and one core's two threads 1.12× (MR37), so each core's stream is bound by the latency of its own ownership reads, not by the controller's bandwidth. An idle sibling online costs CPU 0's wr16m 5.3% (MR38; core-2's).
- **Not the RTL** (tb_boot with memcal.bin, two `smt2` cores, the board's L2, a DDR of 14–30 cycles with readies at 90%; cycles per byte, the chase per load). The model matches the board on both images except in one row:

  | memcal | u100's RTL | d4r2's (ef44e5b7) | model, u100 vs d4r2 | board, u100 vs d4r2 |
  |---|---|---|---|---|
  | memset-16M | 0.467 | 0.486 | −4% | **+18.4%** |
  | memcpy-8M | 0.706 | 0.750 | −6% | −5.3% |
  | memset-1M | 0.469 | 0.492 | −5% | −4.8% (u100's first run) |
  | memcpy-1M | 0.709 | 0.757 | −6% | −5.2% |
  | read-8M | 0.211 | 0.257 | −18% | −22% |
  | chase-4M | 54.9 | 64.8 | −15% | −19% |

  - None of the PL side's mechanisms: the L2 never holds a read beat the memory offers (0 cycles at a fixed latency, 31 in a million beats with jitter), so the injectors' and memory slices' buffering (gone since DR-177 and DR-186) had nothing to absorb; at a 60-cycle DDR u100's path still leads (37.65 against 40.72 cycles a line); a 16 MiB stream through Sv39's 4 KiB pages (4,096 walks a pass) runs 30.80 cycles a line with PMP at fill on or off, against d4r2's 31.05.
- **The controller's pattern** (board MR39; soc-2's wsd.bin: 16 MiB of line writes with k idle cycles after each line; cycles per line):

  | k | 0 | 4 | 8 | 12 | 16 |
  |---|---|---|---|---|---|
  | u100 | 38.3 | 29.9 | 32.7 | 39.5 | 46.4 |
  | d4r2 | 32.0 | 33.7 | 34.6 | 40.0 | 46.6 |
  | the model, u100 | 30.1 | 30.8 | 32.7 | 39.4 | 46.4 |

  - Four idle cycles a line make u100's stream 28% faster, and 7% faster than d4r2's best. The model fits from k = 4 on and misses only k = 0.
  - **Why:** the stream's AXI trace in tb_boot shows each bank's ownership reads and write-backs strictly alternating, a write-back 5 cycles after each read and 1 MiB away, so the PS DDR controller turns its bus round on every request. u100's shorter path (9–12 cycles less a round trip) put the two ports in a phase this controller handles badly; k = 4 moved them out of it. Relying on phase would be fragile.
- **The fix: the L2's write-back batching** (`tg_l2_bank` `WB_PACE`, [l2.md](l2.md) §Victims; a KV260 tuning, [area_switches.md](area_switches.md) §Platform tunings). Each bank holds its ready write-backs until a batch is ready, one has waited long enough or no buffer is left, then sends them back to back, so the controller turns once a batch.
  - `TG_L2_WB_PACE=1` builds it (8 write-back buffers a bank); the host-control block's `L2_PACE` ([host.md](host.md)) sets the batch and the wait at run time, `TG_L2_PACE_INIT` at reset. Off, the default, it is cycle-identical (the Linux boot's first 20M cycles, `st`, `smt2` and `smt2` with hart 1).
  - In the model it costs nothing (30.1 cycles a line unbatched, 29.9 with batches of 4–8) and halves the read/write turns at batches of 2 a port. A batch of B needs about (B − 1) × 64 cycles of wait at a stream's pace.
  - The cost: about 80 LUTs and 66 FFs a chip, no RAM.
  - **On the board:** pending. spikes-2's measurement image (6c41bb53 with rc3_u095r's flow, the batching off at reset) and `tests/bench/mem` `wsdp.bin`, which sweeps the batch and the wait; the setting that wins becomes the KV260 product build's `TG_L2_PACE_INIT`.

## 9. Debug module (`TG_DEBUG`, DR-190 item 4; development builds only)

Status: agreed with core-2 (2026-10-24), whose half is core-priv.md's "Debug mode". The uncore's side is built behind `TG_DEBUG` (soc-2: `rtl/uncore/debug`, `sw/debugrom`, `tests/unit/dbg`); tb_boot's halt, step and resume of Linux comes with core-2's Sdext.

**Purpose.** Halt a hung board, read and write its registers and memory, and step it, with GDB through OpenOCD. OpenOCD runs on the laptop and reaches the RISC-V over the KV260's USB-JTAG (the coordinator, 10-24): that path works in every mode, including RISC-V mode, where the A53 is parked (DR-172). A JTAG port the A53 could drive (AXI GPIO, OpenOCD's `remote_bitbang`) is left out; it would be a small add-on behind its own switch.
- **The switch:** `TG_DEBUG` (off by default; `tg_map_pkg::DEBUG_WINDOW` on the SoC's side, `tg_core_pkg::DEBUG_ON` in the core; `sim/profile.mk` `DEBUG=1`, `build.tcl` `TG_DEBUG=1`) builds the Debug Module, the DTM and the cores' debug mode. A release build has none of them (`build.tcl` refuses it beside `TG_RELEASE=1`), and a build without the switch is cycle for cycle the one before.
- **Sources** (DR-138): the RISC-V Debug Specification 1.0 (ratified 2025-02-21; its register sources at the tag `1.0`) for everything below; AMD UG974 for BSCANE2, and UG570 and UG1085 for the device's TAP; OpenOCD's manual for its configuration only. No other implementation is read.
- **The cable:** OpenOCD and Vivado's `hw_server` share the board's one USB-JTAG cable, so only one of them holds it at a time.
- **Split of the work:** the DTM, the Debug Module and their place in the uncore are this section's (soc-2). The hart's debug mode (Sdext: `dcsr`, `dpc`, `dscratch0`/`1`, `dret`, halt at commit, step, `ebreak` into debug mode) is core-pipeline's and core-priv.md's (core-2).

### 9.1 Structure
```
laptop: GDB ── OpenOCD ── USB-JTAG ── device TAP ──USER3──> tg_dtm (dtmcs)          TCK
                                                 └──USER4──> tg_dtm (dmi) ──CDC──> tg_dm   clk (tg_uncore)
                                                                                   │  ├─ DMI registers
                                    tanager_soc: dbg_haltreq[h] to the cores' debug_req_i
                                    the debug window 0x1100_0000 behind the boot ROM's crossbar port: fetch, loads, stores
```
- `kv260_top` (`DEBUG_WINDOW`): two BSCANE2s, `JTAG_CHAIN` 3 and 4. Every BSCANE2 gives the TAP's same TCK, TDI and state outputs (UG974), so the DTM takes them from USER3's and SEL from each; TCK goes through a BUFG. `tanager_soc` and `tg_uncore` carry them as `jtag_tck_i`, `jtag_i` (`tg_uncore_pkg::jtag_t`) and `jtag_tdo_o`; testbenches tie them off or drive them from a TAP model.
- `tg_uncore` (`g_dbg`): `tg_dtm`, `tg_dm`, and a split of the boot ROM's crossbar port between `tg_bootrom` and the window (one message at a time across the two). `tg_dm`'s `ndmreset` goes into the host bridge's reset levels. Without the switch, none of it: the ROM's port as before, TDO and the halt requests 0.
- `tanager_soc`: each core's `debug_req_i` (its one debug port, tied to 0 before) from `dbg_haltreq`, and the harts' unavailability (§9.4).

### 9.2 The DTM (`tg_dtm`; Debug spec "JTAG Debug Transport Module")
- **The registers** are plain data registers of the device's TAP: OpenOCD selects them with its manual's `riscv set_ir dtmcs <USER3>` and `riscv set_ir dmi <USER4>`, no tunnel framing. USER1 stays free for Vivado's debug hub (ILAs). The device's own IDCODE identifies the TAP.
- **`dtmcs`** (32 bits): `version` 1 (the 0.13 and 1.0 DTM), `abits` 7, `dmistat`, `idle` 3, `dmireset` and `dtmhardreset` (write 1), `errinfo` 0 (not implemented).
- **`dmi`** (41 bits: `address` 7, `data` 32, `op` 2): Capture-DR returns the last answer and the status; Update-DR starts `op` 1 (read) or 2 (write) unless the status is sticky. A capture that finds the request still on its way returns 3 (busy) and makes it sticky, as the spec has it, so the next requests are dropped until `dmireset`, `dtmhardreset` or Test-Logic-Reset. `op` 2 (failed) never comes: the DM answers every request.
- **The crossing:** the request's fields sit in TCK flops and a toggle crosses to `clk` through `tg_cdc_bit` (two flops; `xpm_cdc_single` in synthesis); the DM answers the cycle after, and the answer crosses back the same way. `idle` 3 (two Run-Test/Idle cycles) covers the round trip for TCK up to about 50 MHz with `clk` at 100 MHz. `xdc/timing_debug.xdc` gives TCK 30 ns (`jtag_tck`) and makes it asynchronous to the core clock. `dtmhardreset` cannot drop a request on its way; it needs none, since the answer always comes within a few `clk` cycles.

### 9.3 The Debug Module (`tg_dm`; Debug spec chapter 3)
**Registers on the DMI** (others read 0 and ignore writes):

| Address | Register | Implemented |
|---|---|---|
| 0x04, 0x05 | `data0`, `data1` | 32 bits each (`datacount` 2) |
| 0x10 | `dmcontrol` | `haltreq` (per hart), `resumereq`, `ackhavereset`, `hartsello` (HARTSELLEN = log2 of the harts, at least 1), `ndmreset`, `dmactive`. `hartreset`, `ackunavail`, `hasel`, `hartselhi`, `setkeepalive`, `clrkeepalive`, `setresethaltreq` and `clrresethaltreq` read 0 (not implemented). A write applies to the new `hartsel`; while a command runs, `hartsel` and the per-hart bits keep their values |
| 0x11 | `dmstatus` | `version` 3 (1.0), `authenticated` 1, `impebreak` 1, `stickyunavail` 0, `ndmresetpending` (`ndmreset`, or the cores still in the reset it started; a reset the host holds is no ndmreset), the all/any pairs of `halted`, `running`, `unavail`, `nonexistent`, `resumeack` and `havereset` for the selected hart, `hasresethaltreq` 0 |
| 0x12 | `hartinfo` | 0: the data registers are not reachable from the program buffer by an `x0`-based address, and the ROM keeps both `dscratch` registers (`nscratch` 0) |
| 0x16 | `abstractcs` | `progbufsize` 2, `busy`, `relaxedpriv` 0, `cmderr` (1 busy, 2 not supported, 3 exception, 4 halt/resume), `datacount` 2 |
| 0x17 | `command` | Access Register (`cmdtype` 0): `aarsize` 2 or 3, `postexec`, `transfer`, `write`, `regno` 0x1000–0x101F (the GPRs). Other register numbers, `aarpostincrement`, other sizes and command types end with `cmderr` 2; OpenOCD then reaches FPRs and CSRs through the program buffer. Without `transfer`, `aarsize` and `regno` do not matter |
| 0x18 | `abstractauto` | 0 (not implemented) |
| 0x20, 0x21 | `progbuf0`, `progbuf1` | 32 bits each, followed by an implicit `ebreak` |
| 0x40 | `haltsum0` | a bit per hart, halted and available |

- **`dmactive` 0** holds the DM's registers in reset: the halt requests, `hartsel`, `cmderr`, data, program buffer, a running command's state. While it is 0 a write changes `dmactive` alone. The harts' own states (halted, `havereset`) are kept: a halted hart stays in the ROM's loop and is still seen halted once the DM is active again.
- **`ndmreset`** holds every core and the uncore in reset, as the host's `CTRL = 0x3` does (the host bridge ORs it into both levels; holding the cores alone could leave the L2 waiting for a core's message, host.md), but not the DM and the DTM, which take the SoC reset alone. The L2 forgets its lines, so a system restarted this way runs from the boot ROM on what DRAM holds.
- **Halt and resume:** `haltreq` sets or clears the selected hart's halt request, a level on `dbg_haltreq[h]`; the debugger clears it once the hart is halted (or leaves it, to catch a reset). `resumereq` (with `haltreq` 0) clears the hart's `resumeack` and, if the hart is halted, sets its RESUME flag; the ROM answers. A hart that resets ends a command running on it with `cmderr` 4.
- **Busy rules:** while a command runs, reading or writing `data` or `progbuf`, or writing `abstractcs`, `command` or `abstractauto`, sets `cmderr` 1 (if it was 0) and the write is dropped; the running command's own error is then lost. No command starts while `cmderr` is set.

### 9.4 The hart side (agreed with core-2; core-priv.md has the core's half)
- **`dbg_haltreq[h]`** (level, per hart) drives `tg_core`'s `debug_req_i`, the core's one debug port, in hart order as the interrupt lines: core c's line l is hart c·`NUM_THREADS` + l, and the core maps lines to its threads (core-priv.md). The core takes it at commit as the highest-priority interrupt: `dpc` is the next pc to commit, `dcsr.cause` 3, debug mode, and a jump to 0x1100_0800. A hart asleep in WFI wakes for it and then halts. A hart that leaves reset with it set halts before its first instruction. Halted harts ignore it. Split mode makes no difference.
- **Unavailable harts and `havereset`** come from the SoC's side, not from new core ports (core-2, 10-24): a core has one reset, the host bridge's, so `tg_dm` takes it for every hart (unavailable while it is held, `havereset` set, sticky until `ackhavereset`); and `tanager_soc` marks each core's hart 1 unavailable in a build without it (`tg_core_pkg::HART1_ON`). **The limit:** a hart held off at run time by `mtgsmt.HART1_OFF`, which the firmware leaves 0, shows as running; a halt request to it waits, and OpenOCD times out (core-priv.md).
- **Debug mode** (core-2): M privilege, interrupts masked, `dcsr.stopcount` 1 (counters stop), `stoptime` 0 (`time` is the shared ACLINT's), `stepie` 0, **`mprven` 0** (tied: with it writable and the debuggee's MPRV set, the ROM's own accesses to the window would be translated and fault at 0x808 for ever; OpenOCD translates virtual addresses itself, as the spec expects of a debugger when `mprven` is 0). Fetches, loads and stores are untranslated. **`abstractcs.relaxedpriv` 0:** the program buffer's accesses get M-mode's checks (PMP through locked entries). The debug window is reachable in debug mode only: its fetches go through the I$ as the boot ROM's do, and its loads and stores take the MMIO path. PMP checks it as any M-mode access, through locked entries only (core-2, from the RTL: the LSU registers a store's PMP request before its address is known, so an exemption would gate every consumer of it); the firmware locks no entry over the window. Outside debug mode every access to it faults, fetch included: the PMA check comes before the I$, so the window's lines left in the I$ are never used.
- **Entry's priority** is the spec's (core-priv.md): the halt request above `ebreak`, then step. A halt request pending while an `ebreak` commits enters with cause 3 and `dpc` at the `ebreak`.
- **`ebreak` in debug mode** (the program buffer's, or its implicit one) jumps to 0x1100_0800 and changes neither `dpc` nor `dcsr`. **An exception in debug mode** jumps to 0x1100_0808 and changes nothing else: not `mepc`, `mcause`, `mtval` or `mstatus` ("Traps don't take place"; there is no `mtval2` or `mtinst`).
- **`dret`** is serializing like `mret`: at commit it flushes, redirects to `dpc`, takes the privilege from `dcsr.prv`, clears `mstatus.MPRV` when that is below M, and leaves debug mode; the window faults from the very next fetch. Outside debug mode `dret` is an illegal instruction.
- **Step** (`dcsr.step`): after `dret`, exactly one instruction commits, then the next commit is replaced by entry with cause 4 and `dpc` its pc. If the stepped instruction traps, debug mode is re-entered at once with `dpc` the handler's first pc (the trap updates `mepc` and the rest as usual); a stepped WFI is a nop; with `stepie` 0 no interrupt is taken during the step; a stepped `ebreak` with `dcsr.ebreakm/s/u` set enters with cause 1 (core-priv.md has the spec's cause priorities).
- **Lockstep** (verif-2's call): the core emits no commit records in debug mode, and a marker record at entry, where the checker stops: a debugger may change state that Spike cannot follow.

### 9.5 The debug window (`DEBUG_BASE` 0x1100_0000, 64 KiB)
With `DEBUG_WINDOW`, `tg_xbar` routes `l1i` and `mmio` requests in the window to the boot ROM's port (`route_a`; before, an `l1i` Get there went to the error responder), where `tg_uncore` hands them to `tg_dm`; without it they go where they went before (the device bus, which answers nothing there, or the error responder). `tg_dm` answers Gets of up to 64 bytes (the I$'s line refills and the hart's loads) and single-beat Puts (the hart's stores), as `tg_bootrom` does, one message at a time. All of it sits in the first page; the rest reads 0:

| Offset | Contents | Hart access |
|---|---|---|
| 0x000 + 4·h | FLAGS of hart h: bit 0 GO (run the abstract area), bit 1 RESUME | read |
| 0x100 + 4·h | HALTED: written on entering the loop (sets halted; ends a command the hart took) | write (any value) |
| 0x140 + 4·h | GOING: written as the hart takes GO (clears GO). `abstractcs.busy` stays set until HALTED or EXCEPTION | write |
| 0x180 + 4·h | RESUMING: written before `dret` (sets `resumeack`, clears halted and RESUME) | write |
| 0x1C0 + 4·h | EXCEPTION: written from 0x808 (ends the command, `cmderr` 3) | write |
| 0x200, 0x204 | `data0`, `data1` | read, write |
| 0x300 | The abstract area: 8 words, generated from the running command | fetch |
| 0x340 | `progbuf0`, `progbuf1`, then `ebreak` (`impebreak`) | fetch |
| 0x800 | The ROM's entry (a jump past 0x808) and its halt loop | fetch |
| 0x808 | The ROM's exception entry | fetch |

The status words are decoded by address, so the DM needs no hart id in the data, and the window has room for 16 harts.

**The ROM** (`sw/debugrom/debugrom.S`, built into `rtl/uncore/debug/tg_debugrom_img_pkg.sv` by `make -C sw/debugrom`; `check` verifies the committed image, as the boot ROM's): 30 instructions at 0x800–0x877.
- At entry (from a halt, a step, `ebreak`, or the program buffer's closing `ebreak`) it saves `s0` and `s1` in `dscratch0` and `dscratch1`; at `halt` (0x814) it sets `s0` to the window's base and `s1` to the base plus 4·`mhartid`, writes HALTED, and loops reading its FLAGS word.
  - GO: write GOING, `fence.i` (the DM has just changed the abstract area or the program buffer, and the I$ may hold stale lines; core-2), then jump to 0x300.
  - RESUME: write RESUMING, restore `s0` and `s1`, `dret`.
- 0x808 (an exception in the program buffer, where the registers are the hart's own): save `s0` and `s1` as at entry, write EXCEPTION, and go on as the loop. No exception can come from the ROM or the abstract area: their only accesses are to the window, which faults in debug mode only if a locked PMP entry denies it, and the firmware locks none there.

**The abstract area** (words at 0x300, from the latched command; `s0` is the window's base there, `s1` free):

| Word | Contents |
|---|---|
| 0 | the transfer: `sd`/`sw xr, 0x200(s0)` to read GPR r, `ld`/`lw xr, 0x200(s0)` to write it (a 32-bit write sign-extends); for `s0` or `s1`, `csrr s1, dscratchN` or `ld`/`lw s1, 0x200(s0)`; a `nop` without `transfer` |
| 1 | for `s0` or `s1`: `sd`/`sw s1, 0x200(s0)` or `csrw dscratchN, s1`; else a `nop` |
| 2 | without `postexec`: `j halt` (back to the loop, which writes HALTED: the command's end); with it, `csrr s0, dscratch0` |
| 3, 4 | `csrr s1, dscratch1`; `j 0x340`: the program buffer runs with the hart's own registers, and its `ebreak` re-enters the ROM, whose HALTED ends the command |
| 5–7 | `ebreak` |

## History and lessons

**Starting point (2026-10-13):** the uncore and the KV260 flow, built with stub cores. That first build closed 100 MHz with WNS +2.463 ns, but synthesis removes most of the uncore when nothing drives it.

**KV260 timing at 100 MHz** (WNS, [fpga/kv260/results.md](../../fpga/kv260/results.md)):

| Build | WNS |
|---|---|
| stub cores | +2.463 ns |
| first traffic-generator build | +0.928 ns |
| after R15 | +1.701 ns |
| after the primitive-check fixes | +1.093 ns |
| UART and L2 tables in `tg_ram_lut` | +1.457 ns |
| trace streaming on HP3 | +1.306 ns |

Since R15 the worst path is the L2's S2 decision into the directory RAM. Builds since then range from +1.09 to +1.70 ns, though none of the later changes targeted that path.

**Changes and what each bought:**

| Step | Result |
|---|---|
| Traffic-generator build (the first real uncore timing) | WNS +0.928 ns; the uncore was about 24K LUTs against the plan's 13.3K, 18.4K of it in the L2 |
| L2 lever R15 ([l2.md](l2.md)) | 9.9K → 5.1K LUTs per bank; KV260 WNS +1.701 ns |

**Bugs found:**
- **Core, `tg_fetch`:** an I$ refill that outlives a redirect rewrote the victim way while its old tag stayed valid. Linux executed 4 instructions of another line and oopsed.
  - Found from the commit trace (`+dump_pc`) and a testbench probe on the fetch unit. The race fired about 10 times in 27 M cycles, first inside OpenSBI.
  - Lockstep had not seen it: the test programs fit in the I$. Fixed by the core track.
- **Host program, `tg start` (found by the board session, 2026-10-14):** it released the uncore without setting the DRAM window. The window resets to base 0, size 0, and size 0 denies every access, so the generators would have counted errors, not passes.
  - `tb_soc` writes the window itself before it starts the generators, so no test ran `tanager-host`'s own sequence.
  - Fixed: `tg start` writes the window from `--base`/`--size` while cores and uncore are held, as `load` does.
- **Found on the board in stage B (2026-10-14):**
  - **`tanager-host` read the PL with no design loaded.** The board session ran it after the default app was back; the read went unanswered and the ARM hung until a power cycle. `tanager-host` now refuses unless the overlay's node is in the live device tree (`--force` skips the check).
  - **Options after the command were ignored:** the option string began with `+`, which stops getopt at the command. They now go anywhere.
  - **The injector's native-latency average read 0.1 cycles.** A 32-bit cast around a 16-bit time difference made the subtraction 32 bits wide, so each read in flight across the time counter's wrap added 2^32 − 2^16. The unit test ran shorter than one wrap; it now runs past one and checks the average against the maximum.
- **Interface margin:** a trace sink that stalls from registered occupancy needs 3 × `COMMIT_WIDTH` + `LLT_ENTRIES` of headroom, not `TRACE_STALL_HEADROOM`'s 2 × `COMMIT_WIDTH` + `LLT_ENTRIES` (verification.md §2.9).
  - The SoC run with the test core overflowed a lane at 2 ×.
  - The unit test's core model now has the two-stage stall latency, so it catches the smaller margin.

**From other tracks:**
- **2026-10-14, core track (DR-120):** `tg_map_pkg::pma_of` matches its naturally aligned power-of-two regions by prefix: 10 LUTs per instance instead of 136 and 17 CARRY8, with identical results for every address. `tg_xbar`'s address decode uses it too. The range test is kept for any unaligned region, and `tg_core` warns at elaboration if one appears.

**Lessons:**
- **A test bench that repeats the host program's register sequence does not test the host program.** `tb_soc` took its sequence from this document, not from `tanager-host.c`, and only `tanager-host` had the bug.
- **Take a difference of wrapping counters in their own width.** A wider cast around the subtraction widens the subtraction too. And run every counter-based statistic past its counter's wrap in its test.
- **Time the whole core in context before planning its clock.** Each unit met its own timing run, yet two paths that cross four or five units are 13.5 ns long; the first full build found them.
- **Measure the uncore as its own unit.** A traffic-generator bitstream trims every port its generators leave idle (14.7K LUTs against 22K measured).
- **Group LUTRAM fields by the engine that reads them.** `opt_design` removes primitives behind unused read ports, which failed the primitive check.
- **Run every queued Vivado or simulation job on a snapshot** (`git archive`). A job that starts later otherwise measures whatever the working tree holds by then.
- **A Kconfig choice silently keeps its default when its dependency is unset in the seed.** `INITRAMFS_COMPRESSION_NONE` needs `INITRAMFS_SOURCE` in the seed.
- **Verilator `--threads 4` was slower than one thread** for the 1×1 SoC.
- **Dead end:** the xPack toolchain's `ld` lacks PIE, which OpenSBI needs. OpenSBI is built with the Bootlin toolchain.
- **QEMU first:** QEMU `virt` places its CLINT, PLIC, UART and DRAM where our map does. OpenSBI, Linux and the device tree booted there (§6) before any RTL ran them, so the RTL boot's problems were the RTL's.
