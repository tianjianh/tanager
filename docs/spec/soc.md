# SoC top, KV260 integration and software images

Status: draft — soc track — 2026-10-13

## 1. `tanager_soc` (simulation top and the FPGA's SoC core)

### Purpose
Assembles the cores and the uncore (plan §3.1):
- `N_CORES` `tg_core` instances;
- `tg_xbar` with the cores' ports;
- the L2 (2 banks), each bank's memory path (latency injector → DRAM window → an AXI4 master port);
- the device bus with ACLINT, PLIC, UART and host control;
- the boot ROM;
- the host bridge.

It is board-independent: the same top runs in Verilator with AXI memory models and inside `kv260_top` with the PS.

### Interface
| Port | Domain | Contents |
|---|---|---|
| `clk`, `rst` | core | the core clock; synchronous SoC reset (MMCM lock and PS reset, synchronised by the board top) |
| `clk_host`, `rst_host` | host | host bridge AXI4-Lite side |
| `s_axil_*` | host | host AXI4-Lite slave ([host.md](host.md)) |
| `host_irq_o` | host | to `pl_ps_irq0` |
| `m_axi_*[N_MEMPORTS]` | core | one AXI4 master per L2 bank: 128-bit data, 40-bit address (already remapped onto the carve-out), 6-bit ID |
| `trace_*` | core | each core's commit-trace ports, passed out for simulation harnesses; inside, `tg_trace_stream` streams them into DDR and drives each core's `trace_stall_i` ([uncore-trace.md](uncore-trace.md)) |
| `m_axi_trace_*` | core | the trace stream's AXI4 write master (AW, W, B; no reads): 128-bit, 40-bit PS physical address, one ID; `S_AXI_HP3_FPD` on the KV260 |
| `status_o` | core | LEDs and debug: reset states, L2 init, UART activity |

### Parameters
| Parameter | Default | Meaning |
|---|---|---|
| `N_CORES` | `NUM_CORES` | 1 for M4 (single agent), 2 from M8 |
| `BOOT_ADDR` | `BOOTROM_BASE` | `boot_addr_i` of every core; bare-metal simulation passes `DRAM_BASE` |
| `CLK_HZ` | 100 000 000 | core clock (ACLINT tick, UART timeout, reported to the host) |
| `L2_SETS`, `L2_MSHR`, `L2_DATA_LAT` | 1024, 24, 2 | [l2.md](l2.md). `kv260_top` passes its own `L2_DATA_LAT` (`build.tcl` `TG_L2_DATA_LAT`), whose default 0 picks 4 above 150 MHz and 2 otherwise; any other value is used as it is (DR-146) |
| `CORE_RST_INIT`, `UNCORE_RST_INIT` | 1, 1 | host `CTRL` reset value; simulation testbenches use 0, 0 |
| `DRAM_BASE_INIT`, `DRAM_SIZE_INIT` | 0, 0 | DRAM window at reset; simulation uses base 0 and the model's size |
| `UNCORE_DSP` | `64'h84_0308_0000`: the sites that met 200 MHz as DSPs (the device bus's A slice, the L2 banks' C slices, the memory ports' W slices) | register slices whose main data register sits in DSP48E2s, one bit per site (`tg_uncore`; [uncore.md](uncore.md), DR-136): bits 31:0 the crossbar's, 41:32 the memory ports' AR, AW, W, R and B, 43:42 the L2 banks' R slices. `build.tcl` takes it from `TG_UNCORE_DSP` |
| `AR_SLICE`, `B_SLICE`, `D_SLICE`, `W_SLICE`, `XBAR_IN_SLICE`, `XBAR_SLICE`, `MEM_SLICE` | 1, 0, 0, 0, `4'b0000`, 1, 1 | `tg_uncore`'s register slices ([uncore.md](uncore.md), [uncore-mem.md](uncore-mem.md); what each costs and buys is in §Reserve levers). `tanager_soc` and `kv260_top` pass them on, so a build or a fit sets them without RTL edits (DR-146); `build.tcl` takes each from `TG_` and its name (`TG_XBAR_IN_SLICE` 0–15). The defaults live in `tg_uncore_pkg`, with `UNCORE_DSP`'s |
| `DEBUG_CNT` | 0 | the board debug counters and the cores' board-debug words (`tg_core` `DBG_WORD`) ([uncore.md](uncore.md) §Board debug counters; `build.tcl` `TG_DEBUG_CNT`) |

| `HOST_DMA` | 0 | the coherent host DMA port, `s_axi_dma_*` (§8.1, [host.md](host.md); `build.tcl` `TG_HOST_DMA`). Off, the port is ignored and its outputs are 0 |
| `CORE_KIND` | `"core"` | `"core"`: `tg_core` (the stub until the core track's RTL lands); `"trafgen"`: `tg_trafgen` traffic generators in the cores' place, for bring-up and timing runs before the core exists (§2.3) |

### Behaviour
- **Resets.** The uncore resets on `rst` or the host's `CTRL[1]`; the cores also reset on `CTRL[0]`. Each unit registers its own copy of the reset (conventions §4).
- **Interrupts.**
  - `irq_mei`, `irq_sei`: PLIC contexts 2h and 2h+1.
  - `irq_mti`, `irq_msi`: ACLINT.
  - `irq_ssi`: tied 0.
  - `mtime_i`: the ACLINT's `mtime_o`.
  - `merr_o`: PLIC sources 16 + h, edge-triggered.
- **Memory ports.** `N_MEMPORTS` = the number of L2 banks (2).

## 2. `kv260_top` and the Vivado flow

### 2.1 Board top
`fpga/kv260/rtl/kv260_top.sv`:
- **PS block design** (generated by Tcl, below).
- **`tg_clkgen`:** one MMCM fed by `pl_clk0` (100 MHz) that produces `clk_core` (`CORE_MHZ`: 100 for M4; DR-145 sets 125 MHz preferred and 100 MHz minimum for v1) and `clk_host` (100 MHz). The VCO is 1200 MHz when `CORE_MHZ` divides it, otherwise the first multiple of 100 MHz in 800–1600 MHz that `CORE_MHZ` divides in eighths (CLKOUT0's fractional divide): 125 MHz is 1000 / 8. A multiple of 100 MHz keeps `clk_host` an integer divide.
- **Reset synchronisers:** `pl_resetn0` and MMCM lock into each domain.
- **`tg_axi4_to_axil`:** from `M_AXI_HPM0_FPD` (AXI4, 32-bit data) to the host bridge.
- **`tanager_soc`.**
- **Memory ports:** the SoC's two AXI4 masters drive `S_AXI_HP1_FPD` and `S_AXI_HP2_FPD` (128-bit, clocked by `clk_core`). The commit-trace stream writes through `S_AXI_HP3_FPD` (its read channels are tied off). The 40-bit addresses are zero-extended to the ports' 49.
- **Host DMA:** `M_AXI_HPM1_FPD` (128-bit, clocked by `clk_core`, 2 GiB at `0x5_0000_0000`) goes to the SoC's DMA port when `HOST_DMA` is set, and to `tg_axi_absent` otherwise (§8.1).
- **Fan** (DR-129): pin A12 (`som240_1_c24`, `fan_en_b`, active low) carries the PS timer's PWM, so Linux's `pwm-fan` driver and its thermal zone keep regulating the fan whatever bitstream is loaded.
  - The block design enables TTC<n>'s waveform outputs on EMIO (`PSU__TTC<n>__WAVEOUT__ENABLE`, `__IO = EMIO`, pins `emio_ttc<n>_wave_o[2:0]`), and `kv260_top` drives `fan_en_b` from the right bit, inverted if needed, as Kria's own PL design does.
  - A bitstream loaded at run time does not reconfigure the PS, so the boot configuration already routes the waveform to EMIO; the PL only connects it.
  - **As read from the board:** TTC0 channel 2 (`emio_ttc0_wave_o[2]`), to A12 uninverted. The facts are in `tools/tcl/tg_kv260_fan.tcl`, shared with spike S1 (`TG_FAN_TTC`, `TG_FAN_WAVE`, `TG_FAN_INVERT` override them).
  - On the board, `fancontrol` maps the AMS's temp1 to pwm1, from 15/255 at 35 °C to 255 at 45 °C. The overlay keeps the `pwmfan` node.
- **PMOD console** (`PMOD_UART`; `TG_PMOD_UART=1` in the build): the RISC-V console UART on the PMOD connector, for a USB-UART module (DR-126). The details are in [fpga/kv260/README.md](../../fpga/kv260/README.md).
  - The line runs 8N1 at the 16550's divisor (115 200 baud after OpenSBI), through `tg_uart_phy` ([uncore-periph.md](uncore-periph.md) §UART).
  - The host bridge keeps a copy of the output and can still send input.
  - Off, `pmod_uart_txd` is high-impedance.
  - The pins are PMOD J2 pins 1 and 2, where the board's CH340 USB UART sits (COM5 on the laptop): H12 for TXD (`som240_1_a17`) and B10 for RXD (`som240_1_b20`), as the board session read them.

### 2.2 PS configuration
Block design `tg_ps` in Tcl (`fpga/kv260/tcl/ps_bd.tcl`), board part `xilinx.com:kv260_som:part0:1.4` with the board preset applied (DDR, MIO, clocks), then:
- `M_AXI_HPM0_FPD` enabled, 32-bit, at `0xA000_0000` (64 KiB used), clocked by `clk_host`;
- `S_AXI_HP1_FPD`, `S_AXI_HP2_FPD` and `S_AXI_HP3_FPD` enabled, 128-bit, clocked by `clk_core`; address apertures covering all of DDR (the device-tree overlay sets the three ports' AFI widths);
- `pl_clk0` = 100 MHz; `pl_resetn0`; `pl_ps_irq0[0]` from `host_irq_o`;
- everything else off.

The block design's ports become a wrapper that `kv260_top` instantiates.

### 2.3 Traffic generator (`tg_trafgen`)
A synthesisable stand-in for a core, with the same TileLink ports.
- **On the board:** under host control, through spare host-control registers, it runs a memory test through the L2 and the DDR path:
  - `l1d`: `AcquireBlock`, a data pattern from an address hash, `ReleaseData`, then re-acquire and check;
  - `l1i` and `mmio`: line `Get`s and device reads.
- **In timing runs:** it keeps the uncore's logic from being optimised away while the core is a stub. The build with `tg_core` stubs (`CORE_KIND = "core"`) is the brief's first bitstream target and checks the tie-offs. The `"trafgen"` build is the meaningful timing number for the uncore.

### 2.4 Flow
Non-project Tcl, run only through `tools/vivado_run.sh` (conventions §9):

| Script | Does |
|---|---|
| `fpga/kv260/tcl/build.tcl <cfg> <kind> <mhz> <outdir>` | in-memory project; board part; `ps_bd.tcl`; read RTL through `tools/tcl/tg_files.tcl` (config package, `rtl/rtl.f`, `fpga/kv260/kv260.f`); XDC; `synth_design`; `opt_design`; `place_design`; `phys_opt_design`; `route_design`; reports; bitstream |
| `fpga/kv260/xdc/kv260.xdc` | pin and I/O standard of the fan; clocks come from the PS and MMCM (derived automatically) |
| `fpga/kv260/xdc/timing.xdc` | asynchronous clock groups between `clk_core` and `clk_host` (the host bridge's crossings are XPM macros with their own constraints) |

- **Outputs kept:** `timing_summary.rpt`, `utilization.rpt` (hierarchical), `clock_utilization.rpt`, `cdc.rpt`, `drc.rpt`, the primitive-count check (`primitives.rpt`), and `tanager.bit.bin` (bootgen) for the FPGA manager (`xmutil`).
- **Loading under Linux:** a bitstream loaded at run time does not reconfigure the PS. `fpga/kv260/dtbo/tanager.dtso` is the device-tree overlay that sets `pl_clk0`, the fabric-interface widths (`xlnx,afi-fpga`) and a UIO node for the host window. `fpga/kv260/README.md` is the build and bring-up runbook.
- **Deleted after each run:** checkpoints, run directories and logs (conventions §9).
- **Pblocks:** later (spike S6, plan §7.5).

## 3. Boot flow and memory layout

Plan §7.2. With `DRAM_BASE` = `0x8000_0000`:

| Address | Contents | Loaded by |
|---|---|---|
| `0x8000_0000` | OpenSBI `fw_jump.bin` (generic platform) | host |
| `0x8020_0000` | Linux `Image` with the initramfs built in (`FW_JUMP_ADDR`) | host |
| `0x8220_0000` | DTB (`FW_JUMP_FDT_ADDR` = OpenSBI's generic default, `FW_TEXT_START + 0x220_0000`); OpenSBI skips its copy when the DTB is already there | host |

1. Every hart starts in the boot ROM. It sets `a0 = mhartid` and `a1 = DTB_ADDR`, then jumps to `BOOT_ENTRY` (host control; reset values `0x8220_0000` and `0x8000_0000`).
2. OpenSBI picks the cold-boot hart and boots Linux at `0x8020_0000` in S-mode. Linux brings up the other harts through SBI HSM.

The kernel's effective size (the `Image` header's `image_size`) must stay below 32 MiB, or it would overlap the DTB. `sw/build_linux.sh` checks this.

## 5. Software images

- **Pins:** `sw/versions.sh` (OpenSBI 1.9, Linux 6.18.56, Buildroot 2026.08, Bootlin `riscv64-lp64d` glibc toolchain 2026.08-1 with GCC 15.3, and for `tanager-host` the Bootlin `aarch64` musl toolchain 2026.08-1 with GCC 15.3). `sw/fetch.sh` downloads into the one shared download directory and checks SHA-256 sums recorded in `sw/sha256sums`, which match the upstream published sums. The aarch64 toolchain is unpacked under `$SOC_BUILD/tc` and its archive deleted; `make -C sw/host` builds a static, stripped `tanager-host` (about 75 KB).
- **`sw/build_linux.sh`:** Buildroot with the external tree `sw/buildroot`. The configuration `tanager_lp64d` builds:
  - a busybox initramfs, built into the kernel uncompressed (inflating its 7 MB would add an estimated hour or two to an RTL simulation);
  - Linux from `board/tanager/linux.config` (a small seed: no modules, no EFI, only the platform's drivers);
  - OpenSBI `fw_jump`;
  - the device trees.

  Output goes to `$SOC_BUILD/br-<config>/images`.
- **Board image:** the lp64d image. F/D integration moves into M3, before the board (plan §11), so no soft-float userland is built.
- **`/etc/init.d/S99tanager`:** prints `TANAGER-BOOT-OK` with the hart count. With `tanager.autotest=1` on the command line, it runs a short smoke test and powers off, so QEMU, simulation and board runs end by themselves.

## 6. QEMU proof

`sw/qemu/boot_test.sh` boots the same images on `qemu-system-riscv64 -M virt` with `tanager-qemu.dtb`. The tree is the KV260 tree with one difference: the power syscon points at QEMU's `sifive,test0` device at `0x10_0000`, which takes the same values. QEMU `virt` places its CLINT, PLIC, UART (IRQ 10) and DRAM at the addresses our map uses, so OpenSBI and Linux see our device-tree structure on real devices.

The test passes when the log shows OpenSBI's banner, all harts online (`TANAGER-BOOT-OK … harts=N`) and the autotest's end marker, and QEMU exits through the power-off device.

## 7. Board setup (KV260)

These steps need a person. The coordinator collects them ([host.md](host.md) for the software side):
1. The KV260 boots its standard Ubuntu image from SD, on the network, reachable by SSH with a key.
2. **Carve-out:** the RISC-V DRAM window must be invisible to A53 Linux. The default plan is to boot with `mem=3G`, which leaves the top 1 GiB of the high DDR bank (`0x8_4000_0000`–`0x8_7FFF_FFFF`) unused. A `reserved-memory` node with `no-map` is the alternative. Spike S1 confirms the method and the SMMU bypass (plan §5.5).
3. **SMMU:** the HP ports pass through the SMMU. If the board's Linux makes unknown stream IDs fault, add `arm-smmu.disable_bypass=0` to the kernel command line. Spike S1 confirms whether this is needed.
4. **Load:** as the PL app `tanager` through dfx-mgr's `xmutil`, as for spike S1. The app is `tanager.bit.bin`, `tanager.dtbo` (the overlay above) and `shell.json` in `/lib/firmware/xilinx/tanager/`; then `xmutil unloadapp` and `xmutil loadapp tanager`. `fpga/kv260/package.sh` puts the files together with `tanager-host`.
5. **Host program:** `tanager-host` is copied to the board and run as root. The bring-up steps and their expected results are in `fpga/kv260/README.md`.

### 7.1 Unanswered PL reads and the PS's AXI timeout block

A read on `M_AXI_HPM0_FPD` that no PL slave answers never completes, and the A53 hangs until a power cycle. The board session hung the board this way on 2026-10-14 by running `tanager-host` with the default app loaded. `tanager-host` now refuses unless the overlay's node is in the live device tree (`check_overlay`). The PS also has a hardware guard for this, the AXI timeout block (ATB), which is not enabled on this board.

- **What it is:** one ATB per PS-PL master path; it tracks transactions and, on a timeout, answers the PS master itself and raises an interrupt.
  - **Registers:** `FPD_SLCR` at `0xFD61_6000` (AMD's `xfpd_slcr.h`, Vivado 2025.2's embeddedsw).
  - **One bit per path** in each register: bit 0 FPDS (the switch to the SIOU slaves), bit 1 AFIFS0 (`M_AXI_HPM0_FPD`, our host bridge; UG1087, `ERR_ATB_ISR`) and bit 2 AFIFS1 (`M_AXI_HPM1_FPD`).
  - **Register map:** `ERR_ATB_ISR` `+0x00` (sticky, write 1 to clear), `IMR`/`IER`/`IDR` `+0x04`/`+0x08`/`+0x0C`, `ATB_CMDSTORE` `+0x10` (reset 7), `ATB_RESP_EN` `+0x14` (reset 0: **off**), `ATB_RESPTYPE` `+0x18` (reset 7), `ATB_PRESCALE` `+0x20` (enable at bit 16, value in bits 15:0, reset `0x0000_FFFF`: **off**). The LPD has the same block at `0xFF41_6000`.
- **How AMD's proposed Linux driver uses it** (`zynqmp_atb.c`, posted to the kernel lists in May 2025; not in the board's 6.8 kernel):
  - **Sequence:** clear `ATB_RESP_EN`, set `ATB_RESPTYPE` and `ATB_CMDSTORE` to the chosen paths, set `ATB_PRESCALE = 0x10100` (enabled; "based on 100 MHz clock"), clear `ERR_ATB_ISR`, then set `ATB_RESP_EN` and `ERR_ATB_IER`.
  - **Response:** on a timeout the ATB returns SLVERR, which the program sees as a bus fault. The driver logs "atb: Timeout detected".
  - **Its stated limit:** "only a limited number of AXI timeouts can be registered before the bus will eventually stall".
- **Option A: `tanager-host` enables the ATB on AFIFS0 before its first PL access** (the sequence above, for bit 1 only).
  - **Pros:** an unanswered read becomes a bus fault (SIGBUS) instead of a hang. It also covers what the device-tree check cannot: a design that is loaded but does not answer (clock or reset stopped, a wedged bridge).
  - **Cons:**
    - It writes PS configuration registers from user space; a wrong address can disturb the PS.
    - Whether `/dev/mem` may write `FPD_SLCR` on this firmware is unknown (an XPPU can block it).
    - The timeout formula is not in the sources we have, so the prescaler value needs a measurement.
    - The setting outlives the program, and applies to whatever design is in the PL, until reboot.
    - By AMD's own note it absorbs only a few timeouts.
- **Option B: enable it at boot**, through the proposed driver or a systemd unit that writes the same registers.
  - **Pros:** it protects every program and logs every timeout.
  - **Cons:** the driver is not in the board's kernel, and a boot unit changes the board's setup, which is the board session's area.
- **Option C: the device-tree check alone** (what `tanager-host` does now, with the board session's `xmutil` check in `tg.sh`).
  - **Pros:** it touches no PS registers.
  - **Cons:** it does not protect a loaded design that stops answering.
- **Recommendation:** keep C, and try A on the board once, behind an explicit `tanager-host` command rather than by default.
  - **First step:** read the ATB registers (reads of PS registers are safe) and confirm the reset values above.
  - **Then:** enable AFIFS0 only, and read `0xA000_0000` deliberately with the default app loaded. The expected result is a bus error, not a hang.
  - **Needs the user's consent:** if the ATB does not engage, that read hangs the board, and only a power cycle recovers it.
- **Sources:** `xfpd_slcr.h` and `xlpd_slcr.h` (AMD embeddedsw in the Vivado 2025.2 install); UG1087, `ERR_ATB_ISR (FPD_SLCR)`; the `zynqmp_atb` patch series (lwn.net/Articles/1022531, May 2025); a PYNQ forum thread with similar writes but a different prescaler encoding (`0x1020`; it does not report the result).

### 8.1 Stage C: the board's peripherals through the ARM (virtio)

The RISC-V's Linux uses storage, then network and entropy, through virtio-mmio devices whose back-ends run on the A53 (`tanager-host`). Slots: `0x1001_0000`, 4 × 4 KiB (console, block, network, rng), PLIC sources 1–4 (already reserved in the device tree and the device bus).

**Where the virtio-mmio registers live:**

| Option | How | Pros | Cons |
|---|---|---|---|
| **C-a: registers in the uncore** | The virtio-mmio register set per slot in RTL (features, queue select, sizes, addresses, ready, status, interrupt status and ACK, configuration space). The host reads and writes the registers through its window. | Register reads at bus speed. | About 1–2K LUTs for four slots against an uncore already over budget. RTL for every new field or device type. |
| **C-b: a forwarded window** (chosen, DR-147) | RISC-V accesses to a slot become requests in a small queue the A53 serves. Reads wait for the answer; writes are posted. Interrupt status and ACK stay in RTL, so taking an interrupt needs no round trip. | Little RTL: a request FIFO, a response register and the interrupt bits. Every virtio device type is software in `tanager-host`. | A register read waits for the A53, about 10–100 µs. Linux's driver reads registers at probe time; at run time it writes QueueNotify (posted) and handles interrupts locally. The device-bus path must tolerate long stalls (it has no timeout). |

**The forwarded window (C-b).** A device-bus target at `0x1001_0000`–`0x1001_3FFF`, four 4 KiB slots.
- **Accesses:**
  - The control registers are 32-bit.
  - The configuration space also takes 8- and 16-bit accesses (virtio-mmio requires them for narrow fields), so a request carries its size.
- **Forwarded:** every access except two registers of each slot. A queue entry is {slot[1:0], offset[11:0], size[1:0], we, wdata[31:0]}.
  - Writes are posted: the device bus acknowledges once the entry is queued.
  - A read waits in the same queue behind earlier writes, and holds the device-bus response until the host answers (`tg_tl_dev`'s wait input, [uncore.md](uncore.md) §Device bus). The device bus has no timeout.
  - The queue (16 entries, LUTRAM, an asynchronous FIFO into `clk_host`) back-pressures the device bus when full.
  - 64-bit accesses answer denied: virtio-mmio uses 8-, 16- and 32-bit ones.
- **Local:** InterruptStatus (`0x060`) and InterruptACK (`0x064`) of each slot are answered in RTL, so taking an interrupt needs no round trip.
  - Each slot has two status bits: bit 0, used buffer; bit 1, configuration change.
  - The host sets the bits through a register, and the driver's InterruptACK clears them.
  - The bits' OR is the slot's PLIC source, 1–4, level-triggered.
- **Host registers** (host bridge, `clk_host`, `0x1100`–`0x1114`; the layout is in [host.md](host.md)):
  - `VQ_CTRL`: `EN`, the host serves the window;
  - `VQ_STATUS`: the queues' counts, a read waiting, the slots' status bits;
  - `VQ_REQ0`, `VQ_REQ1`: the oldest entry in two words; reading the second pops it;
  - `VQ_RSP`: a write completes the waiting read with its data;
  - `VQ_IRQ`: sets or clears the slots' status bits.
  - `VQ_RSP` and `VQ_IRQ` cross in one 16-entry event queue, so the RISC-V side sees them in the host's order.
  - A host interrupt bit (`IRQ_STATUS[4]`, on `pl_ps_irq0`) is raised while the queue is not empty.
- **Not served** (`EN` = 0, its reset value): the window answers every access itself, reads with 0 and writes by dropping them. Linux's virtio-mmio driver then finds no device (`MagicValue` 0) instead of waiting forever for a host that isn't there, so a device tree can list the slots in every build that has the window.
- **Switch:** `tg_uncore` `VIRTIO_WINDOW` (`TG_VIRTIO_WINDOW=1`; off by default, cycle-identical when off). The slots then answer denied, as before. `CAPS[2]` says which.

**The coherent host DMA port.** Virtqueues and buffers are in RISC-V memory, and the back-end reaches them through this port, so neither side does cache maintenance. `/dev/mem` on the carve-out would read DDR behind the L2's dirty lines, so it can't be used.
- **Path:** `M_AXI_HPM1_FPD` (128-bit, clocked by `clk_core`; 2 GiB at `0x5_0000_0000` in the block design, so AXI address bits [31:0] are the offset into the RISC-V's RAM, below `DRAM_SIZE`), then the AXI4-to-TileLink bridge `tg_hdma` (TL-UH: `Get`, `PutFullData`, `PutPartialData`, one 64-byte line per message), then the crossbar's `hdma` initiator (`tg_xbar` `HOST_DMA`), then the L2.
- **AXI4 rules:** INCR bursts; FIXED and WRAP answer `SLVERR`. One read burst and one write burst at a time, each with one line message in flight, so responses are in order.
  - **A read** takes each line its burst touches with one `Get` and returns the beats in order (a narrow beat carries its 16-byte lane).
  - **A write** gathers each line by byte strobe, then sends it as one `PutFullData` (all 64 bytes written) or `PutPartialData` (with the masks), and takes the next line's beats after the `AccessAck`.
  - Beyond `DRAM_SIZE` nothing is forwarded: a read beat answers `DECERR`, a write beat is dropped.
  - **Writes always answer OKAY.** On the A53 an error on a posted write is an asynchronous SError, which panics its Linux (the Cortex-A53 has no RAS extension); a read's error is a synchronous abort, a SIGBUS to the reader. A write burst not done in full counts in `HDMA_WR_DROPS` ([host.md](host.md)).
- **Without the port** (`HOST_DMA` = 0) the block design still has HPM1, and `kv260_top`'s `tg_axi_absent` answers it: reads with `DECERR`, writes dropped with OKAY. A stray A53 access then fails instead of hanging the ARM.
- **Coherence:**
  - The L2 serves the port coherently. A read sees the cores' dirty lines (the L2 probes the owner first).
  - A write completes, with AXI B, only after the L2's AccessAck, which follows the invalidation of every L1 copy.
- **Lockstep:** with `HDMA_CTRL[0]` set, each written line's `AccessAck` queues a completion, {line, cycle}, in a 16-entry queue the host pops through the host bridge (`HDMA_CPL0`, `HDMA_CPL1`); a write waits while the queue is full. The cycle is the trace records' capture count: `tg_hdma` keeps its own copy, which a simulation assertion checks against the trace stream's. `tanager-host` hands (address, data, cycle) to `tanager-lockstep` as external-write records ([verification.md](verification.md) §3.10). No DMA data enters the trace stream.
- **Switch:** `tg_uncore` `HOST_DMA` (`TG_HOST_DMA=1`; off by default, cycle-identical when off). `CAPS[8]` says which.

**Notification and completion.** A QueueNotify write reaches the A53 as a forwarded request. The back-end then works the virtqueue through the DMA port, updates the used ring, and sets the slot's status bit with `VQ_IRQ`. The driver's InterruptACK clears it.

**`tanager-host` back-ends** (a virtio-mmio device model per slot, version 2 registers), in this order:
1. **virtio-blk** on an image file on the A53's filesystem: `tanager-host run --blk <image>`. Later the RISC-V's own SD partition (below).
2. **virtio-net:** a TAP device on the A53, bridged with its Ethernet (`br0`), so the RISC-V gets its own address on the LAN. The bridge is an A53 OS change: approved in advance (DR-147), set up with an automatic rollback, and logged with its undo in `fpga/kv260/README.md`, as every A53 change of stages C and D is.
3. **virtio-rng:** from the A53's `getrandom()`.

The console stays the 16550 UART (PMOD, with the host's copy). Debian's kernel has no SBI console tty, so the console must be a UART.

**The boot chain** (a standard SBC's):

### 8.2 Stage D: dual boot, the RISC-V drives the PS's peripherals

After the A53 boots it hands the board to the RISC-V and parks. The RISC-V's own drivers then run the PS's SD, GEM Ethernet, USB and UART controllers. Each OS has its own SD partition.

**The PL-to-PS path.**
- An uncore target window (a device region of the RISC-V map) with an AXI4-Lite master into `S_AXI_LPD` reaches the IOP peripherals' registers (`0xFF00_0000`–`0xFFFF_FFFF`; to confirm in the TRM that `S_AXI_LPD` reaches them).
- Device accesses are at most 8 bytes, so AXI4-Lite suffices.
- The XPPU must allow that master to reach these peripherals.

**Interrupts.** The PS routes the four peripherals' interrupts to the PL (the PS-to-PL interrupt signals, enabled in the PS configuration). They go to free PLIC sources, for example 20–27.

**Peripheral DMA.**
- The SD, GEM and USB controllers are bus masters that write DDR through the PS interconnect, behind the RISC-V's L2.
- **Addresses** are a device-tree matter: `dma-ranges` maps RISC-V RAM (`0x8000_0000`) to the PS bus address the controllers must use.
- **Coherence** with the L2 has three options:

| Option | How | Pros | Cons |
|---|---|---|---|
| **D-a: cache maintenance** | Zicbom in the core (`cbo.clean`/`cbo.inval`) and flush and invalidate by address in the L2. Linux's non-coherent DMA operations then work (`riscv,cbom-block-size`). | Standard. No copies. Direct DDR bandwidth. | RTL in the core and the L2 (Zicbo* is planned for M9), so stage D waits for it. Maintenance costs CPU time per buffer. |
| **D-b: bounce buffers** | An uncached alias of part of the carve-out: a PMA region the L2 does not cache, routed straight to the memory port. Linux's `restricted-dma-pool` (swiotlb) bounces all peripheral DMA through it. | No core changes; ready for M5. | Every DMA buffer is copied once. The pool's size limits the I/O in flight. A small uncore change: an uncached route in the crossbar. |
| **D-c: DMA through the PL into the L2** | `dma-ranges` points the controllers at a PS bus address inside an HPM window (PS to PL), which the host bridge forwards into the coherent host DMA port of §8.1. The controllers' DMA then reaches the L2 like the A53's back-end does. | Coherent, with no core changes and no copies. Reuses stage C's DMA path. | DMA bandwidth is that of the HPM port and the L2's `hdma` initiator, enough for SD, USB 2 and 1 GbE but not for USB 3 at full speed. Longer latency. The HPM window is shared with the host window (decoded by address). **To confirm** in the ZynqMP TRM and on the board: that these IOU masters can target an HPM window at all. |

  Decided (DR-147): D-c. Debian's kernel drives no non-coherent DMA device without Zicbom, so D-b, whose uncached pool needs a core PMA change, and D-a wait. D-a becomes possible when Zicbom lands (M9).

**The handover sequence** (what the A53 leaves configured):
1. **Boot:** the PMU firmware and FSBL set up the PLLs, MIO pins, resets and DDR. ATF, U-Boot and the A53's Linux follow.
2. **Prepare:** `tanager-host` loads the bitstream and the RISC-V images. The RISC-V device tree describes the peripherals it will own.
3. **Release the devices:**
   - The A53 unbinds its drivers for those controllers and keeps their clocks and resets as they are (`clk_ignore_unused`, or held clock references).
   - The A53 can't keep its root filesystem on the SD card it gives away. It runs from an initramfs, or unmounts the SD first.
   - The SD tap delays, which the A53's driver sets through firmware calls, stay programmed in the IOU registers.
4. **Open the protections:**
   - The SMMU passes the controllers' stream IDs through, or maps them as an identity.
   - The XMPU lets their DMA reach the carve-out (or the HPM window for D-c).
   - The XPPU lets `S_AXI_LPD` reach their registers.
   - This may need a custom PMU-firmware isolation configuration.
5. **Park:** the secondary A53 cores go off (PSCI `CPU_OFF`). The boot core waits in a WFI loop. The PMU firmware keeps running (power management, watchdog).
6. **Release the RISC-V** (core reset off). Its Linux probes the controllers.

**The RISC-V device tree.**
- The four controllers get nodes with the generic compatibles: `arasan,sdhci-8.9a`, `cdns,gem`, `snps,dwc3` and `cdns,uart-r1p12`. The ZynqMP-specific ones call EEMI firmware through ARM SMC, which the RISC-V doesn't have.
- **Clocks** are `fixed-clock` nodes at the rates the A53 left.
- **Interrupts** go through the PLIC; **DMA** uses the `dma-ranges` above.

**Risks:**
- drivers that assume the ZynqMP firmware for resets, tap delays or PHY setup;
- the PMU firmware's default isolation;
- the PS-to-PL interrupt routing for USB;
- the A53's Linux re-gating clocks it thinks are unused.

Each is checked on the board in stage D's first step, with the UART: the simplest controller, no DMA.

**The fan in stage D** (DR-129). With the A53 parked, its Linux no longer regulates the fan: the TTC keeps its last duty cycle. Options:

| Option | How | Pros | Cons |
|---|---|---|---|
| **F-a: PL controller** | A small controller reads the PL SYSMON's die temperature (SYSMONE4, DRP) and sets the PWM from a fixed curve. | Works without any OS, and keeps working if software hangs. | RTL (an estimated 200 LUTs plus the SYSMON primitive). A fixed curve. Our own thermal policy to get right. |
| **F-b: RISC-V Linux** | The RISC-V's Linux drives the same TTC (the `pwm-cadence` driver over the PL-to-PS port) with `pwm-fan` and a thermal zone reading the PS's AMS or the PL SYSMON. | The same regulation as on the A53, in software. | Depends on the RISC-V's Linux running. If it hangs, the fan stays at the last duty, possibly low. Needs the TTC and a temperature sensor in the RISC-V's device tree. |
| **F-c: both** | F-b regulates, and a minimal F-a acts as a floor: full speed above a temperature threshold, else the TTC's PWM passes through. | Normal regulation from Linux, and safety if either OS hangs. It also protects stage B, should the A53's Linux stop. | Both pieces exist: a comparator and a multiplexer on top of SYSMON in the PL, plus the RISC-V's drivers. |

**Chosen (DR-147): F-a as a full regulator** that keeps the A53's control while it is there.
- **Duty:** the PL drives `fan_en_b` with its own 25 kHz PWM. Its duty is the larger of two:
  - a fixed curve of the PL SYSMON's die temperature (SYSMONE4 over DRP, piecewise-linear with hysteresis, full speed above a top threshold);
  - the A53's TTC duty, which the PL measures from `emio_ttc0_wave_o[2]`.
- **Stages B and C:** the A53's `fancontrol` stays in charge whenever it asks for more than the curve. DR-129 holds: the TTC waveform still reaches the fan.
- **Stage D, or if any OS hangs:** the curve regulates alone.
- **Why not F-b or F-c:** Debian's kernel has no `pwm-fan`, no TTC PWM driver and no temperature driver for this chip. So the RISC-V's Linux would need two or three of our own modules before it could regulate, and the fan would still depend on that Linux running. With F-a the fan never depends on the RISC-V's software, and no new driver is needed.
- **Monitoring:** a read-only register (temperature, duty, source) can be added later for a small driver.
- **Clean room:** no SiFive-compatible PWM is needed. If one is ever added, it is built only from SiFive's published register manual (DR-138).

**Stage C against stage D.** C needs only the host DMA port and a little RTL, and the A53 does the I/O. D gives the RISC-V the whole board at native speed. Its costs are the PL-to-PS bridge, the interrupt routing, DMA coherence, the handover and firmware-free drivers. C stays useful after D, as a fallback and for devices the RISC-V can't drive.

**Stage D's DMA must be coherent** (the verification track's kernel check). Debian's kernel handles a non-coherent DMA device only with Zicbom or T-Head's cache operations, and Tanager has neither. So D-c, DMA through the PL into the L2, is required, not just preferred.

**Stage D's drivers.** Debian's kernel has MACB, PHYLIB and DP83867, as modules. It lacks `sdhci-of-arasan`, `dwc3`, `xilinx_uartps`, any TTC PWM, `pwm-fan` and the AMS driver. Those are our own modules, using generic compatibles and no ZynqMP firmware calls. The fan needs none: the PL regulates it (below).

### 8.3 PL cost of stages C and D (estimate, DR-147)

| Lever | Saves | Costs | How often it costs (measured) |
|---|---|---|---|
| **L2 same-set rule at S0** (e256b0e, reverted in fc1031e): hold S0 while a request of the same set is in S1 or S2, in place of the directory's two-entry write-history bypass. With `L2_DIR_S3` (on since 498aaa1) the directory is written a cycle later, so the rule would also hold for S3: up to three bubbles, against a three-entry bypass | 518 LUTs at st and at smt2 (uncore budget unit: 22,783 → 22,265 at smt2; 425 when it was first measured). ## History and lessons

**Starting point (2026-10-13):** the uncore and the KV260 flow, built with stub cores. That first build closed 100 MHz with WNS +2.463 ns, but synthesis removes most of the uncore when nothing drives it.

**KV260 timing at 100 MHz** (WNS, [fpga/kv260/results.md](../../fpga/kv260/results.md)):

| Build | WNS |
|---|---|
| stub cores | +2.463 ns |
| first traffic-generator build | +0.928 ns |
| after R15 | +1.701 ns |
| after the primitive-check fixes | +1.093 ns |
| UART and L2 tables in `tg_ram_lut` | +1.457 ns |
| trace streaming on HP3 | +1.306 ns |

Since R15 the worst path is the L2's S2 decision into the directory RAM. Builds since then range from +1.09 to +1.70 ns, though none of the later changes targeted that path.

**Bugs found:**
- **Core, `tg_fetch`:** an I$ refill that outlives a redirect rewrote the victim way while its old tag stayed valid. Linux executed 4 instructions of another line and oopsed.
  - Found from the commit trace (`+dump_pc`) and a testbench probe on the fetch unit. The race fired about 10 times in 27 M cycles, first inside OpenSBI.
  - Lockstep had not seen it: the test programs fit in the I$. Fixed by the core track.
- **Host program, `tg start` (found by the board session, 2026-10-14):** it released the uncore without setting the DRAM window. The window resets to base 0, size 0, and size 0 denies every access, so the generators would have counted errors, not passes.
  - `tb_soc` writes the window itself before it starts the generators, so no test ran `tanager-host`'s own sequence.
  - Fixed: `tg start` writes the window from `--base`/`--size` while cores and uncore are held, as `load` does.
- **Found on the board in stage B (2026-10-14):**
  - **`tanager-host` read the PL with no design loaded.** The board session ran it after the default app was back; the read went unanswered and the ARM hung until a power cycle. `tanager-host` now refuses unless the overlay's node is in the live device tree (`--force` skips the check).
  - **Options after the command were ignored:** the option string began with `+`, which stops getopt at the command. They now go anywhere.
  - **The injector's native-latency average read 0.1 cycles.** A 32-bit cast around a 16-bit time difference made the subtraction 32 bits wide, so each read in flight across the time counter's wrap added 2^32 − 2^16. The unit test ran shorter than one wrap; it now runs past one and checks the average against the maximum.
- **Interface margin:** a trace sink that stalls from registered occupancy needs 3 × `COMMIT_WIDTH` + `LLT_ENTRIES` of headroom, not `TRACE_STALL_HEADROOM`'s 2 × `COMMIT_WIDTH` + `LLT_ENTRIES` (verification.md §2.9).
  - The SoC run with the test core overflowed a lane at 2 ×.
  - The unit test's core model now has the two-stage stall latency, so it catches the smaller margin.

**From other tracks:**
- **2026-10-14, core track (DR-120):** `tg_map_pkg::pma_of` matches its naturally aligned power-of-two regions by prefix: 10 LUTs per instance instead of 136 and 17 CARRY8, with identical results for every address. `tg_xbar`'s address decode uses it too. The range test is kept for any unaligned region, and `tg_core` warns at elaboration if one appears.

**Lessons:**
- **A test bench that repeats the host program's register sequence does not test the host program.** `tb_soc` took its sequence from this document, not from `tanager-host.c`, and only `tanager-host` had the bug.
- **Take a difference of wrapping counters in their own width.** A wider cast around the subtraction widens the subtraction too. And run every counter-based statistic past its counter's wrap in its test.
- **Time the whole core in context before planning its clock.** Each unit met its own timing run, yet two paths that cross four or five units are 13.5 ns long; the first full build found them.
- **Measure the uncore as its own unit.** A traffic-generator bitstream trims every port its generators leave idle (14.7K LUTs against 22K measured).
- **Group LUTRAM fields by the engine that reads them.** `opt_design` removes primitives behind unused read ports, which failed the primitive check.
- **Run every queued Vivado or simulation job on a snapshot** (`git archive`). A job that starts later otherwise measures whatever the working tree holds by then.
- **A Kconfig choice silently keeps its default when its dependency is unset in the seed.** `INITRAMFS_COMPRESSION_NONE` needs `INITRAMFS_SOURCE` in the seed.
- **Verilator `--threads 4` was slower than one thread** for the 1×1 SoC.
- **Dead end:** the xPack toolchain's `ld` lacks PIE, which OpenSBI needs. OpenSBI is built with the Bootlin toolchain.
- **QEMU first:** QEMU `virt` places its CLINT, PLIC, UART and DRAM where our map does. OpenSBI, Linux and the device tree booted there (§6) before any RTL ran them, so the RTL boot's problems were the RTL's.
