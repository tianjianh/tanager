# Shared L2 (`tg_l2`, `tg_l2_bank`)

Status: draft — soc track — 2026-10-13

## Purpose

The L2 is the shared last-level cache and the coherence point of the memory system (plan §5.1–5.3). It holds 1 MiB in UltraRAM, in 2 banks interleaved on address bit 6. It serves the cores' TL-C `l1d` agents and TL-UL clients (`l1i` refills, uncached `mmio` accesses to DRAM, host DMA). It fetches and writes back lines through one 128-bit AXI4 master per bank.

**Growth path.** One RTL serves M4 and M8:
- **M4:** a single core, so one agent.
- **M8:** the coherent dual core.

The directory, probes and race handling below are written for `N_AGENTS` agents from the first commit. M4 builds and verifies them with one agent; with one agent, probes still occur (an `l1i` refill of a line its own L1D holds dirty, an eviction of a line the L1D holds, an uncached write). M8 adds multi-agent verification (Murphi/Rumur model, plan §9) and the stream prefetcher (§Prefetch).

## Interface

Per bank (the interconnect delivers each bank only its own addresses; [uncore.md](uncore.md)):

| Group | Direction | Contents |
|---|---|---|
| A | in | `tl_a_t`: `AcquireBlock`, `AcquirePerm`, `Get`, `PutFullData`, `PutPartialData` |
| B | out | `tl_b_t`: `ProbeBlock` to agent `source[7:6]` |
| C | in | `tl_c_t`: `ProbeAck[Data]`, `Release[Data]` |
| D | out | `tl_d_t`: `GrantData`, `Grant`, `AccessAckData`, `AccessAck`, `ReleaseAck` |
| E | in | `tl_e_t`: `GrantAck` |
| AXI4 master | out | AR/R/AW/W/B, 128-bit data, `PA_W` address, `AXI_ID_W` IDs; bursts of 4 beats, INCR |
| Status | out | `init_done`; event pulses for performance counters (hit, miss, writeback, probe) |

The AXI master sees a generic memory at the RISC-V physical address. Remapping onto the KV260 carve-out, the latency injector and the PS port live outside the L2 ([uncore-mem.md](uncore-mem.md)). No KV260 or PS constant appears in the L2 (plan §14).

## Organisation (per bank)

| Item | Value (default build) |
|---|---|
| Capacity | 512 KiB: `SETS` = 1024 sets × 8 ways × 64 B |
| Address split | `tag = addr[PA_W-1:17]` (17 bits), `set = addr[16:7]`, `bank = addr[6]`, offset `addr[5:0]` |
| Data array | `tg_ram_sdp`, `PRIM = "ultra"`: 256-bit rows, 32 byte enables, 16 K rows = `{set, way, half}`; 16 URAM (4 wide × 4 deep, plan §5.1) |
| Directory (tag) array | `tg_ram_sdp`, block RAM: one row per set holding 8 way entries and the set's PLRU bits. Each entry, and the PLRU, fills whole bytes with its own write enables (3 bytes per entry at 1–4 agents; 200-bit rows) |
| Way entry | `tag`, `valid`, `dirty` (newer than DRAM), `pres[N_AGENTS]` (agent holds the line), `tip` (the one present agent holds T) |
| Replacement | tree PLRU (7 bits per set) |
| MSHRs | `N_MSHR` = 24 (plan §5.1: 48 in total); MSHR `m` also names the transaction as sink `{bank, m}` and as AXI ID `m`. State flags in flip-flops; the fields written at allocation in multi-read-port LUTRAM (§MSHR file) |
| Write-back buffers | `N_WB` = 4 lines |
| Put data buffers | `N_PUTBUF` = 4 lines (data and byte mask) |

**Directory states** (plan §5.2, MESI in the L1D):
- `pres = 0`: no L1D holds the line.
- `pres ≠ 0, tip = 0`: the agents in `pres` hold it in B (S).
- `tip = 1`: exactly one agent is present and holds T (E or M; it may be dirty in its L1D without the L2 knowing).

The L2 is inclusive of every L1D: an agent can hold a line only while the L2 holds it.

## Behaviour

### Request pipeline

Every directory read and write goes through one three-stage pipeline per bank:
- **S0:** arbitration and the directory RAM read;
- **S1:** RAM latency;
- **S2:** decision, the directory write and MSHR allocation.

Pipeline requests, highest priority first:

| Kind | From | Purpose |
|---|---|---|
| `INIT` | reset sequencer | write every set invalid (1024 cycles after reset); A, C and E stay not-ready until done |
| `REL` | C input | `Release` / `ReleaseData` |
| `PACK` | C input | `ProbeAck` / `ProbeAckData` |
| `MCMD` | an MSHR | resume a transaction (after probes; after a fill error) |
| `ACQ`, `GET`, `PUT` | A input | a new client request |

- **Directory read-modify-write.** Every S2 request writes back its selected way entry and the PLRU bits (`INIT` writes them all), through the byte enables. A request does not enter S0 while a request of the same set is in S1 or S2, because its read would not see that request's write (the RAM is read-first, with its data two cycles after the read). The highest-priority waiting request holds S0 meanwhile, so the order of C, MCMD and A requests is unchanged. Same-set requests back to back are rare, because A requests of one set go one at a time anyway (rule 2). The cost is at most two bubbles, where a write-history bypass put a row of multiplexers on the S2 path.
- **C input.** It takes one message at a time and gathers all beats of `ProbeAckData` / `ReleaseData` before entering the pipeline. It takes the next message only after the current one's data is written and its `ReleaseAck` is queued. C messages are never blocked by MSHRs (TileLink 1.8.1 §8.2: the manager must accept a voluntary Release while it is probing the line).
- **A input.** It gathers the beats of a multi-beat `Put` into a free Put buffer. It enters the pipeline only when all of these hold:
  1. no active MSHR has the request's line as its request line or as its victim line;
  2. no request **for the same set** is in S1 or S2 (the same-set rule above, which holds for every request kind). Victims are chosen at S2, so an older same-set request may be about to evict this line; once it is past S2, its MSHR's victim line is visible to rule 1;
  3. no `Release`/`ProbeAck` carrying data for the line is in the pipeline or still writing its beats (the C message updates the directory at S2 and writes its data in the following cycles);
  4. free MSHRs exceed the `ACQ`/`GET`/`PUT` requests in S1–S2;
  5. MSHRs reserving a way in the set number fewer than the ways.

  Rules 4–5 are conservative, so an A request that enters always finds an MSHR and a way at S2. The random test found the need for rules 2 and 3: without them a request could read DRAM ahead of a write-back, or read a line before a Release's data reached the array.
- **One transaction per line.** Rule 1 serialises all client transactions on a line. This is the bank's whole ordering discipline: TileLink races between transactions on one line cannot arise, and the remaining races (a Release crossing a Probe) are handled as below.

### Transactions

An A request that enters the pipeline always gets an MSHR. At S2 the bank reads the set's row:
- **hit:** the line's way;
- **miss:** a victim way, chosen in this order:
  1. an invalid way;
  2. among ways not reserved by an active MSHR, the PLRU choice if its `pres` is empty, else the lowest-numbered way with empty `pres` (plan §5.1: prefer victims no L1 holds);
  3. otherwise the PLRU choice among unreserved ways.

  The way a `Release`/`ProbeAck` is still writing data into counts as reserved, so a victim read-out never overtakes those writes.

Then:

**Acquire** from agent `a` (`AcquireBlock` / `AcquirePerm`; `NtoB`, `NtoT`, `BtoT`):
1. **Hit.** Probe set:
   - `NtoB`: the owner, if `tip` and the owner is not `a`, with cap `toB`.
   - `NtoT` / `BtoT`: every present agent except `a`, with cap `toN`.
   - If the set is empty, write the final directory entry now: `pres[a] = 1`; `tip = 1` for `NtoT`/`BtoT`, and for `NtoB` when no other agent is present (an E grant, interfaces.md §2.3). Then respond. Otherwise probe first, then resume (§Probes).
2. **Miss.** Issue the AXI read at once. Handle the victim (§Victims). Write the new tag with `pres[a] = 1`, `tip = 1` (no other L1 can hold a line the inclusive L2 lacks), `dirty = 0`. When the fill is written, respond.
3. **Response.**
   - `AcquireBlock`: `GrantData` (4 beats) read from the data array, `param = toT` or `toB`, `sink = {bank, m}`. GrantData is sent even for `BtoT`, so the data is always current (TileLink 1.8.1 §8.2 requires current data when the agent may have been probed since its Acquire).
   - `AcquirePerm`: `Grant` (no data).
   - The MSHR is freed when `GrantAck` arrives and its write-back (if any) is complete.
   - **`BtoT` from an agent no longer present:** the agent lost its copy to an earlier probe. It is served as `NtoT`.

**Get** from any client (`l1i`, `mmio`, host DMA; size ≤ 6):
- **Hit:** if `tip`, probe the owner with cap `toB`; its dirty data comes back in `ProbeAckData`, and it keeps a B copy. Then respond.
- **Miss:** like an Acquire miss, with final entry `pres = 0`, `tip = 0`.
- **Response:** `AccessAckData` from the data array: 1 beat (size ≤ 4, the beat holding `addr[4]`), 2 beats (size 5) or 4 beats (size 6).
- Interfaces.md §2.2: instruction lines are not tracked, and every `Get` returns current data.

**Put** from any client (`PutFullData` / `PutPartialData`, size ≤ 6):
- **Hit:** probe every present agent with cap `toN`, resume, write the data with its byte mask, set `dirty`.
- **Miss:** fetch the line, then merge the write. A `PutFullData` of a whole line skips the fetch.
- **Response:** `AccessAck`.

### Probes

The probe set is held in the MSHR (`probe_pending[N_AGENTS]`). A scheduler sends one `ProbeBlock` per cycle on B:
- `source = {agent, 6'b0}`, `size = 6`, the address of the line being probed.
- That line is the request line on a hit, the victim line on a miss.

A `ProbeAck[Data]` from agent `b` enters the pipeline as `PACK`:
- It finds the line's way, which is always present: victims keep their tag until resolved.
- It updates `pres[b]` and `tip` from the report or shrink parameter.
- It ORs in `dirty` and writes any data.
- It clears `b` in the MSHR that is probing that line. That MSHR owns the line's way: its request line on a hit, its victim on a miss. No two MSHRs own one `{set, way}`, so the lookup compares the set and the hit way, not the line.

When `probe_pending` empties, the MSHR requests an `MCMD` resume. The resume re-reads the row, writes the final directory entry and continues: respond, write the Put data, or handle the victim. Every directory change therefore comes from the pipeline, in order.

**Release crossing a Probe** (TileLink 1.8.1 §8.2, Figure 8.6):
1. An agent may send `Release[Data]` for a line the bank is probing.
2. The Release is not blocked. It updates `pres`/`dirty`/data like any Release, and the bank sends `ReleaseAck`.
3. The agent sends its `ProbeAck` only after that `ReleaseAck`, so the `PACK` sees the released state and the MSHR's resume sees the final state.

### Victims

- **Victim not held by any L1:**
  - At S2, write the new line's tag over it.
  - If the victim is dirty, read its 2 rows into a write-back buffer and issue AW + 4 W beats.
  - The fill may start once the read-out is done.
- **Victim held by agents:**
  - Keep the victim's tag in place.
  - Probe its holders with cap `toN`.
  - Resume: the victim is now unheld and its dirty bit is final. Write the new tag, then read out as above.
- **Write-back completion:** the MSHR keeps the victim line until the write-back's B response returns. A request for the victim line waits until then (rule 1), so a re-read can never overtake the write in the AXI fabric.

### Fills and AXI

- **AR:** issued once per miss MSHR, with ID `m`.
- **R:**
  - Accepted for MSHR `m` only once its victim read-out is done (or there is none). Until then R is held: `RREADY = 0` while the beat at the head belongs to such an MSHR.
  - The latency injector delivers whole bursts in issue order ([uncore-mem.md](uncore-mem.md)), so holding R only delays later fills.
  - Each beat is written to its half-row with byte enables, so beats of different IDs may interleave.
- **Error response** (`RRESP ≠ OKAY`) on any beat:
  - The MSHR requests an `MCMD` that invalidates the way.
  - It responds with `denied = 1`, plus `corrupt = 1` on data messages.
  - The requester must not cache the line. For a Grant the agent still sends `GrantAck`.

### Data array ports

- **Write port:** C data (Release, ProbeAck) has the highest priority, then Put data, then fills.
- **Read port:** victim read-outs (they unblock fills), then response data.
- **Credits:** a response reads a row only when the D output queue (8 beats) has room for the row's beats, counting reads still in the RAM pipeline. The queue keeps one LUTRAM entry per row read (one or two beats) and picks each beat's half on the way out.
- **D output:** shared by MSHR responses and `ReleaseAck`s. A data message's beats stay contiguous.

### MSHR file

- **Flip-flops:** the state, the flags the engines set and clear (probes pending and sent, fill and write-back progress, error), and copies of the line, the victim tag and the way for the compares that look at every MSHR at once (admission rules 1 and 5, way reservations, the `ProbeAck` lookup).
- **LUTRAM** (`tg_ram_lut`, written once at allocation): the line's set and tag, the victim's tag (it is in the request's set), the way, and the request fields (kind and grow, source, Put buffer, response shape: AcquireBlock, size, address bits 5:4). Each engine reads them through its own read port by MSHR index, so there are no wide multiplexers over the MSHRs. The fields are grouped by the engines that read them, so every read port uses every bit it reads (the primitive check counts the RAM32M16s after `opt_design`). The bank bit of a line is `BANK`. The fill beat counters are in LUTRAM too: they are read and incremented by the R beat's ID, and the reset sequencer clears them. The write-back buffers' owner and line are a small LUTRAM as well.
- **State transitions:** each event (allocation, MCMD issue and result, last `ProbeAck`, victim read-out start and end, last fill beat, Put written, response sent, `GrantAck`, write-back B) applies to an MSHR in exactly one state. The next state is therefore selected by the current state, with no priority among the events. The simulation asserts the state each event expects.
- **Engine picks:** round robin, as two priority encoders (requests at or above the pointer, then all requests).

### Prefetch (M8)

The stream prefetcher (plan §5.1) will be a pipeline request kind below `ACQ`/`GET`/`PUT`:
- It allocates an MSHR like a `GET` miss, with no response.
- It is dropped when no MSHR or way is free.
- Distance and degree are run-time registers (reset 16 and 4).

The arbiter input exists with `valid = 0` until then.

## Timing and area

- **Hit latency** (L1 miss to first D beat, without interconnect): S0–S2 (3) + MSHR to read issue (1) + URAM read (`DATA_LAT`: 2 with the output register) + D queue (1), about 7 cycles (9 with `DATA_LAT = 4`). The interconnect slices add 2, giving about 9 against the plan's 10–12-cycle load-to-use target. The L1 fill adds its own cycles.
- **Critical paths at 200 MHz:**
  - the S2 decision: 8 tag compares, way select (hit, victim or the MSHR's way), the selected entry's read and update, into the directory RAM's data inputs. The directory write enables depend only on `p2_v_q`: every S2 request writes back its selected entry and the PLRU byte, changed or not. The same-set rule at S0 removed the write-history bypass from this path. The next lever is splitting the compare (S2) from the update (S3); the same-set rule then covers S3 too.
  - the MSHR conflict compare in S0: per MSHR, one set compare shared by the line, victim-tag and same-set checks.
- **URAM cascade:** 4 deep. `DATA_LAT` sets the data array's read latency (`tg_ram_sdp` `RD_LAT`), and the read-tag pipeline follows it. It is 2 (the output register) up to 150 MHz; 4 pipelines the cascade for 200 MHz (spike S6). `tanager_soc` `L2_DATA_LAT` passes it on, and `kv260_top` picks 4 above 150 MHz.
- **R input slice:** a register slice on the AXI R channel keeps the MSHR-state lookup behind `RREADY` inside the bank. It was the stub build's worst path: MSHR state → `RREADY` → injector buffer, 6.6 ns.
- **Area estimate per bank:** about 4–5K LUTs, mostly MSHR control and the conflict compares; 16 URAM; 6–7 BRAM36 (directory, write-back and Put buffers in LUTRAM). This sits in the plan §8.2 uncore line.
- **Measured** (out-of-context synthesis of one bank, `fpga/kv260/tcl/ooc_synth.tcl`; steps and sweep in [fpga/kv260/results.md](../../fpga/kv260/results.md)):
  - **First version (2026-10-13):** 9.9K LUTs and 4.5K FFs at 24 MSHRs and 2 agents, about twice the estimate. Six engines selected MSHR fields by index through 24:1 multiplexers, and each round-robin pick rotated its request vector modulo 24. The 8-beat D queue was in flip-flops with two write ports, and S2 rebuilt and wrote back the 183-bit directory row.
  - **After lever R15 (the same day):** 5.1K LUTs (790 of them LUTRAM) and 2.6K FFs at 24/2; 4.9K at 24 MSHRs and 1 agent (the M4 configuration), 3.9K at 16 and 3.0K at 8. Each MSHR costs about 120 LUTs and 65 FFs. 16 URAM, 6 RAMB36 + 1 RAMB18 (the byte-aligned directory row takes one RAMB36 more).
  - **What remains** (logic cones per register group, `TG_OOC_CONES=1`): MSHR state transitions about 0.8K (ten event sources decoded for 24 MSHRs); the S2 decision about 1.0K; the admission compares; the three 128-bit data multiplexers (D half select, W half select, data-array write data), about 130 LUTs each.

## Verification

`tests/unit/l2`: random traffic against a reference memory, at `SETS = 16` so evictions and probes are frequent.
- **Agents:** behavioural TL-C L1D models (`N_AGENTS` = 1 in M4; 2–4 in M8) with 4–8-line caches.
  - They issue random `AcquireBlock` / `AcquirePerm` (`NtoB`, `NtoT`, `BtoT`), stores into owned lines (which update the reference) and evictions (`Release` `TtoN` / `TtoB` / `BtoN`, `ReleaseData` when dirty).
  - They answer probes by the TileLink rules, including holding a `ProbeAck` until a pending `ReleaseAck`.
- **TL-UL clients:** `Get` and `Put` of every size, and `l1i`-style line `Get`s.
- **Memory:** an AXI4 slave model with random latency, back-pressure and out-of-order responses across IDs, optionally behind the latency injector.
- **Checks:**
  - every Grant and AccessAckData carries the reference value (single-writer: only a T holder changes the reference);
  - permissions never conflict (at most one T, never T and B together);
  - inclusivity holds;
  - every request completes (a watchdog);
  - the AXI rules hold (bursts of 4, `WLAST`, one write-back per eviction).
- **Assertions:** directory invariants at every S2 write; no two active MSHRs on one line; a `PACK` always finds its MSHR; a `REL` always hits.
- **M8:** the coherence model (Murphi or Rumur) of these flows, then multi-agent runs of this test (plan §9).
