# D4: the mode chosen at boot, with the A53 parked in RISC-V mode (plan)

For the coordinator, before any build (soc-2, 10-19). It replaces the kexec handover of DR-164, after the user's correction (10-19):

> "A53 should not always up. arm is only up initially to check which mode to go, if we go riscv mode, A53 should turn over the peripheral and park, everything belongs to riscv. if we go arm mode, everything is a53, no riscv at all."

## The two modes

- **ARM mode,** the default and every fallback: Ubuntu as today. It may load k26-starter-kits, or a Tanager app under `tanager-host`, so stages B and C stay as they are.
- **RISC-V mode:** the A53's U-Boot sets the PS up, loads the Tanager bitstream and the RISC-V's firmware, releases the RISC-V and parks.
  - The RISC-V's OpenSBI and U-Boot (S-mode) load Debian from `p3` through the Arasan SD controller.
  - Debian runs with part A's DKMS modules.
  - No A53 OS, no `tanager-host`, no SSH on the A53. The fan runs on D2's regulator, with the A53's dead PWM ignored.

## The mode record

- **Where:** one raw 512-byte sector in the card's gap before `p1` (sector 2047, checked free in step 0). It holds a magic, the mode (arm or riscv) and a trial flag.
  - U-Boot reads and writes it with `mmc read`/`mmc write`, which every U-Boot has.
  - Ubuntu and Debian write it with a small `tanager-mode` tool (`dd`).
  - If step 0 shows U-Boot has `fatwrite` and the user prefers a file on `p1`, the same fields go in `p1:/tanager/mode` instead.
- **What U-Boot does with it:**
  - A missing, unreadable or invalid record boots ARM.
  - `riscv` with trial 0: set trial to 1, write it back, then RISC-V mode.
  - Trial 1: ARM, because the last RISC-V boot never confirmed.
- **Debian:** a shutdown unit writes `riscv`, trial 0, on every clean shutdown or reboot. `tanager-mode arm` then `reboot` goes to ARM.
- **Ubuntu:** `tanager-mode riscv` then `reboot` goes to RISC-V.
- **So any unclean end of RISC-V mode boots ARM next:** a hang followed by the reset hook, a crash, or a power loss.

## Boot firmware: `p1` only, QSPI untouched

- **What step 0 found** (the board session, 10-19, `fpga/kv260/board/d4/step0_probe.txt`):
  - The QSPI U-Boot is 2023.01 (K26-BootFW-01.02, images A and B the same). It has every command the plan uses: `fpga`, `zynqmp mmio_write`, `mmc read`/`write`, `itest`, `setexpr`, `load`, `source`, `mw`, `md`, `go`, `fatwrite` and `reset`. It has no bootcount.
  - Its environment was never saved, so the defaults apply. The boot goes through distro boot (`mmc1` first) to `p1`'s `boot.scr.uimg`.
  - Sector 2047, like all of sectors 1-2047, is zero. `p1` has 883 MB free.
  - RESET_REASON reads `0x21` after a power-up: bit 5, a soft reset, comes from the boot firmware's own reset into image A. So it can't mark a reset the RISC-V asked for. The trial flag does that.
- **The mode check:** Ubuntu's boot script is generated by flash-kernel from a template, `bootscr.zynqmp.kria`. The template is a conffile of flash-kernel, so it stays untouched. The check goes in a hook file, `/etc/flash-kernel/ubootenv.d/tanager-mode`, which flash-kernel puts in at the template's `@@UBOOT_ENV_EXTRA@@`: at the top level, before the boot loop, where distro boot's `devtype`, `devnum` and `distro_bootpart` are set. In RISC-V mode it does `source tanager/riscv.scr`.
  - flash-kernel regenerates `p1`'s `boot.scr.uimg`.
  - Before the first change, today's script is copied to `boot.scr.uimg.tanager-pre`. The `.orig` from 10-14 lacks `mem=3G arm-smmu.disable_bypass=0`, and `mem=3G` keeps Ubuntu out of the RISC-V's carve-out.
  - A failing `riscv.scr` returns into Ubuntu's script, so that boot continues in ARM mode.
  - **Undo:** delete the hook file and rerun flash-kernel.
- **`p1:/tanager/`** (about 10 MB): `riscv.scr`, `tanager.bit.bin`, `fw_jump.bin`, `u-boot.bin` (S-mode, with the Arasan driver), `tanager-kv260-d4.dtb`. The bitstream is never `p1:/system.bit`: the template loads that file in every boot, ARM mode included.
- **`riscv.scr`, in order.** Any failure before step 7 returns, and Ubuntu boots:
  1. Write trial 1 to the mode record.
  2. Load the bitstream with `fpga load`. Set the PS as the overlay does under Linux: `pl_clk0` at 100 MHz (CRL_APB `PL0_REF_CTRL`), and the fabric widths (`AFI_FS`: HPM0 32-bit, HPM1 128-bit; the HP and LPD ports reset to 128-bit). Pulse `pl_resetn0`.
  3. Read the host bridge's ID through HPM0. Without our design, stop and boot ARM.
  4. The PS for the RISC-V's peripherals:
     - SD1's and UART1's clocks, power and pins stay as the boot firmware left them: U-Boot used both, and no A53 OS powers anything down.
     - SD1's tap delays are set to the A53 Linux's values (`ITAPDLY` `0x012A0000`, `OTAPDLYSEL` `0x00050000`) with `zynqmp mmio_write`.
     - GEM3's PHY reset (MIO38) and USB0's hub reset (MIO44) wait for D5 and D6.
  5. The host bridge: the DRAM window (`0x8_4000_0000`, 1 GiB), the boot entry and DTB address, and `BOARD_CTRL` (the fan ignores the A53's PWM; the PMOD reset hook armed).
  6. Load `fw_jump.bin`, `u-boot.bin` and the tree into the carve-out, at `tanager-host`'s offsets.
  7. Release the uncore, wait for the L2's initialisation, release the cores. This is the point of no return.
  8. Park the boot A53 in a WFI loop: two instructions written to OCM, then `go`. The other A53s are still held by the boot firmware.

## PL changes: one board build, unit tests first

- **`tg_ps_window`:** CRL_APB `RESET_CTRL` (`0xFF5E0218`) passes, that word only (a doubleword would reach the next register), while `BOARD_CTRL` bit 1 is set. Its SOFT_RESET bit resets the PS and the PL.
  - The RISC-V mode tree points `syscon-reboot` (and `syscon-poweroff`) at it. Debian's reboot (SBI system reset, then OpenSBI's syscon-reboot) then resets the board.
  - With bit 1 clear the window is exactly as before, so a RISC-V program under `tanager-host` in ARM mode can't reset the A53's Ubuntu.
- **`tg_host_bridge`:** `BOARD_CTRL` at `0x1404`, reset 0, kept through an uncore reset ([host.md](host.md)).
  - Bit 0: the fan regulator ignores the A53's PWM. In RISC-V mode the A53's TTC is dead. This is DR-154's small interface change, foreseen for D3.
  - Bit 1: the board's reset path, `RESET_CTRL` in the window and the PMOD reset hook armed.
  - Bits 3:2 read back the hook's write: `[2]` it went out, `[3]` it was answered with an error or not at all. Both clear with bit 1, so clearing and setting bit 1 arms the hook again.
- **`tg_uncore`, the PMOD reset hook (in `TG_PS_WINDOW` builds):** while armed, a break on the PMOD UART's RX of 2^28 to 2^30 cycles (2.7 to 10.7 s at 100 MHz) makes `tg_ps_window` write `RESET_CTRL` when the break ends, once per arming.
  - The write goes out at the window's first idle cycle, ahead of any access, whatever the RISC-V is doing. Accesses meanwhile are denied.
  - A transaction that never ends (the PS port blocked) holds the write back too. Then only a power cycle helps.
  - **Why on the break's end, with a ceiling:** a USB-UART adapter that loses power (the laptop's USB off, the cable pulled) holds RX low as well, for as long as it stays off. Firing during the break would reset the board 2.7 s into any such outage. With the ceiling, only an outage of 2.7 to 10.7 s that then ends looks like a break.
  - The laptop sends a 3 s break on COM5 (pyserial's `send_break(3)`).
- **Unaffected:** stages B and C, where `BOARD_CTRL` stays 0 under `tanager-host`. Builds without `TG_PS_WINDOW` have no reset path.

## RISC-V software

- **U-Boot S-mode** (`sw/uboot`, `bash sw/build_uboot.sh d4`; step 3, built 10-19):
  - `MMC_SDHCI_ZYNQ` allowed on RISC-V by `patches-d4/0001`: the Kconfig line, and the ZynqMP-only header `asm/arch/sys_proto.h` left out on RISC-V. The ZynqMP code (the PMU firmware calls, the tap-delay and DLL code, the clock phases) is under `CONFIG_ARCH_ZYNQMP` and compiles out. So the driver runs as a plain SDHCI, and the tap delays stay as `riscv.scr` set them.
  - `DM_MMC`, with the tree's fixed clocks (`sdio1_ref` at 166,666,665 Hz; at most 50 MHz on the card).
  - **PIO, no DMA.** SD1's DMA reaches the RISC-V's RAM only at bus address `0x5_0000_0000`, the host DMA port (the tree's `dma-ranges`). U-Boot's ADMA doesn't apply `dma-ranges`, and its SDMA is 32-bit. Linux's driver uses the DMA API, which does.
  - The Cadence UART driver as well, for a tree whose stdout is UART1.
  - The boot command: extlinux from `mmc 0:3` (`p3`), nothing else. Without it U-Boot stops at its prompt, and the PMOD break or a power cycle gives ARM mode.
- **The RISC-V mode tree** (`sw/dts`, `UART1=1 SD1=1 BOARD_RESET=1`; every other tree byte-identical): UART1 (the stdout, so OpenSBI and U-Boot are on COM7), SD1, and reboot and poweroff as a syscon write of SOFT_RESET to `RESET_CTRL` alone. The boot arguments come from `p3`'s extlinux, Debian's own (its console on the PL UART, COM5).
- **Debian** (`p3`): the `tanager-mode` tool and the shutdown unit (`sw/d4mode/debian_install.sh`). The DKMS modules stay.
- **The boot script** `riscv.scr` ([`sw/d4mode/riscv.cmd`](../../sw/d4mode/riscv.cmd)): the steps listed above. It writes the park loop to OCM first and reads it back, and checks each PS write it depends on by reading it back. A refused tap-delay write is not fatal: it leaves the taps the A53's U-Boot read the card with. On QEMU it runs dry, with board addresses moved into RAM and board-only commands stubbed: to the park, out at once without our design, and out (the uncore held again) without the L2's initialisation.
- **The watchdogs** (step 2's probe): both SWDTs are off when Linux runs (ZMR `0x1C2`, enable bit clear; both `inactive`), so the A53's U-Boot doesn't start them, and nothing needs stopping before the park.
- **The images** are loaded low and copied into the carve-out (`cp.b`). The A53's U-Boot runs from the low 2 GiB ("DRAM: 2 GiB (effective 4 GiB)"), and `cp` takes no part in the memory reservations `load` checks.

## Every failure ends in ARM mode

| Failure | What happens |
|---|---|
| No, invalid or unreadable mode record | ARM |
| `riscv.scr` fails before the release (a file missing, `fpga load`, no host bridge) | The script returns and Ubuntu boots now. The record says trial 1, so ARM next time too |
| The RISC-V fails after the release (OpenSBI, U-Boot, no SD, Debian) | Trial 1 stays. The PMOD break, or a power cycle, resets the board into ARM |
| Debian hangs later | The PMOD break resets into ARM |
| Power loss in RISC-V mode | ARM at power-on |
| A broken boot script | U-Boot's prompt on COM7: source the kept copy (`boot.scr.uimg.tanager-pre`) for Ubuntu, then undo the hook |
