# Tanager

Tanager is a clean-room, 2-wide-decode, out-of-order RV64GC dual-core with two hardware threads per core (SMT2) that runs Linux on the AMD Kria KV260 (XCK26). Its IPC must beat NaxRiscv's, and it is built so 3-wide decode can be added next.

**Status.**
- **M1 (model and design-space exploration):** done. The parameter freeze was approved on 2026-10-13.
- **SMT2 model study:** done ([docs/perf/smt2_report.md](docs/perf/smt2_report.md)).
- **Roadmap:** single-thread bring-up (ST) → **v1, the first release: SMT2, 2-wide, 2 cores × 2 harts** (plan §6.5) → v2: 3-wide on the SMT2 core. All on the KV260 (plan §8.5).
- **Schedule (plan §11):** agent-built. Linux on the board about 4–6 weeks after M0 starts; v1 in about 3 months.
- **M0 (repository, CI, FPGA spikes):** done. Spike S1 ran on the board on 2026-10-14: an idle 64-byte DDR read from the FPGA takes 36.8 cycles (184 ns) at 200 MHz, and the two HP ports together move 6.35 GB/s. The spikes are reported in [docs/perf/spikes.md](docs/perf/spikes.md).
- **M2 (out-of-order core in simulation):** done on 2026-10-14. Lockstep passes in all four configurations; CoreMark 3.04 CM/MHz on the conservative M2 core.
- **M3 (Linux-capable core):** done in simulation on 2026-10-14. RV64GC, with F and D, runs in lockstep with Spike in all four configurations (ACT4 rv64imafdc 895/895), and Linux (OpenSBI, Buildroot lp64d) boots to userspace in Verilator. The area work toward v1's 103K-LUT bar continues as FPGA-native rewrites ([docs/perf/fpga_friendly.md](docs/perf/fpga_friendly.md)).
- **M4 (single core on the KV260):** done on 2026-10-17. The ARM side is up (stage A) and spike S1 is done. Stage B passed on 2026-10-14. First the traffic-generator bitstream: it loads with Linux's fan control, its memory path runs with 0 errors at native and at 250 injected cycles, and the RISC-V console comes out on the PMOD UART. Then **the real out-of-order core booted Linux on the board**: one `st` core at 60 MHz runs the SoC test program to PASS, and boots OpenSBI 1.9 and Linux 6.18 to a root shell and a clean poweroff, at native latency and at 250 injected read cycles, with the console on both the host bridge and the PMOD UART. **FPGA lockstep passed on 2026-10-14:** the A53 checked every one of the 335,786,888 commit records of a Linux boot to a root shell and poweroff against Spike, and none differed; at 250 injected read cycles too (355,612,637 records). M4's last exit criterion, at least 100 MHz, was met with the core at 100 MHz on the board (sc3_100, 2026-10-17).
- **Clock (DR-152):** v1's target is 100 MHz; 115 MHz was dropped for now on 2026-10-17, and a higher clock is taken only where it is cheap. Main meets 100 MHz on the board (sc3_100, +0.347 ns) and in the full chip with the second thread's area reserved (+1.065 ns). The user accepts a few MHz below 100 while M6's features go in (DR-162): with the return-address stack the full chip reaches about 95 MHz. With TAGE-lite as first built it reached only about 66 MHz, because one fetch stage chained 40–44 logic levels; with that stage restructured at no cycle cost (DR-165) and Vivado's ExploreArea optimisation (DR-166), the whole M6 set (the RAS, two-table TAGE, four misses, speculative wakeup) routes at 100 MHz with the second thread's area reserved: +0.725 ns, no failing path, 97.1% of the LUTs. The L1 data cache keeps 4 misses in flight by default (DR-156).
- **M6 (the core's performance features, DR-153):** started on 2026-10-17 alongside M5, measured in RTL simulation first. **The first M6 set is on main (aae0503, 2026-10-18):**
  - four L1D misses in flight (under Linux on the board, a 1 MiB memcpy −38% and /init 8% sooner);
  - speculative load wakeup;
  - a 32-entry return-address stack;
  - TAGE-lite with two tagged tables of 2K entries;
  - returns and straddling compressed instructions predicted at fetch, with a restructured fetch stage;
  - two rename fixes: a store's address no longer waits for its data, and ALU ops are steered with up-to-date queue room.

  CoreMark per MHz (rv64gc, timed regions, RTL simulation) went from 3.06 to 4.55 (flags A) and from 2.79 to 4.27 (B) over M6 so far, and Dhrystone from 1.48 to 3.08 DMIPS/MHz. The last merge alone makes the 20M-cycle Linux boot retire 14% more instructions. It costs about 2.1K LUTs per core, and the full chip still routes at 100 MHz with the second thread's area reserved.

  **Under Linux on the board (2026-10-19, two cores at 100 MHz, three boots):** CoreMark reaches 4.61 (A) and 4.36 (B) per MHz and Dhrystone 2.82 DMIPS/MHz, against 2.77, 2.29 and 1.41 before M6, and Linux reaches /init 21% sooner. Instructions per operation are unchanged, so the whole gain is IPC. The board found a micro-BTB bug that every simulation check had passed: two code blocks 2 MiB apart could share an entry, and decode no longer checked the shared target. It panicked Linux about 2.2 s into the boot. core-2's fix and a short directed test that reproduces it are on main. PMP with 8 entries (DR-167) saves about 2,970 LUTs a chip.

  **The final D4 bitstream (d4r1, 2026-10-19)** adds two M6 pieces aimed at Linux: the store ownership prefetch, where a store asks for write permission on its line as soon as its address is known, and FENCE.I by generation, which stops fetch waiting while the instruction cache is flushed. Against the build before them, page faults are 28% faster, 1 MiB memcpy 35% and memset 29% faster, and Linux reaches /init 10.5% sooner (0.83 s; 1.18 s before M6). CoreMark and Dhrystone are unchanged. Since then, an instruction-cache next-line prefetch (on main, d3e124a) fetches the following line on every miss, for 109 LUTs a core. In simulation, run the way the board runs, it brings /init a further 2.3% sooner.

  **Board time against simulation:** simulating the RTL the way the board runs predicts the board's boot phase by phase. It predicted d4r1's /init at 0.832 s before the board measured 0.831 s.

  **Two RTL performance bugs found by the model (2026-10-20):** rechecking the as-built model against the RTL showed crc32 losing 36% to a load replay racing a store's write to the cache, and the ud benchmark's branch predictor thrashing one entry between two loop exits. Both fixes are on main: crc32 −22.5%, ud −14.7%, huffbench −6.8%. Today's main runs CoreMark at 4.48 (flags A) and 4.42 (B) per MHz and Dhrystone at 3.09 DMIPS/MHz in RTL simulation.
- **M7 (SMT2, the second thread in each core, DR-175):** started on 2026-10-19 on core-2's approved plan, eight steps, each behind a switch and merged with every cycle unchanged while the second thread is off. Steps 1–7 are on main (step 6 at 124edb9f on 2026-10-21, step 7 at 002ea157 on 2026-10-23): thread ids through the pipeline, each thread's own control registers, rename state and queue pointers, the window's static halves, translation and the load/store unit per thread, rename for two threads, a fetch stream, branch history, return-address stack and instruction queue per thread, the second thread running, a rename register per thread (DR-178), commit turns that follow readiness, fetch no longer held by a full queue, decode taking a thread only when rename can take its group, and a run-time switch that turns the second thread off, with its half of the queues returned to the running thread while it sleeps. The FP registers are two banks of 64 per core, and an FP op whose own bank is full renames into the other (DR-179, 1.6K LUTs a core less). **Linux boots on all four threads (two cores × two) under lockstep, and on the KV260 itself (2026-10-22):** a temporary 80 MHz bring-up bitstream (DR-187) boots Linux on all four harts, with CoreMark on each, the atomics test on every pair and harts taken offline and back, without an error, and soaked 11 hours clean. **Since 2026-10-23 four-hart Linux runs at the product clock, 100 MHz** (DR-188's preview image from the first product build to close timing): `/init` at 52 s and the login at 154 s from reset, CoreMark validated on every hart at the same per-MHz figure as the single-thread core, stress 10 of 10, no fault in any log. It's the first hardware run of the PMP checks at TLB fill. Two threads running found six bugs that every one-thread check had passed. **Throughput:** against one program on the whole core, two programs at once do 1.22× its work at 30 cycles of memory latency, 1.19× at 120 and 1.17× at 250 (step 6). The model puts step 7 at about 1.20× (1.24–1.28× at best), under the original 1.3× target, so the user made step 7's measured result the target, with no pair hanging and no loss for one program alone (DR-184). **Step 7 (on main 2026-10-23)** drops the planned per-thread caps for one rule: a thread may not take an issue-queue bank's last row while the other thread waits for a row there. The caps, and the plan's fetch policy (ICOUNT, which favours the thread with fewer instructions in flight), each slowed the two-thread Linux boot by 2–3%. The rule ends the one hang (a stride kernel beside Dhrystone): all 42 program pairs run, 204 of 204, at 1.226× / 1.217× / 1.192× the work of one program, with the boot within noise of main (+0.15% over nine latencies), for about 161 LUTs a core. **Area:** a test chip with the real second thread but without the product's peripheral windows placed at 97.2% of the KV260's LUTs and missed 100 MHz by only 0.096 ns once the L2 banks and the crossbar were floorplanned (DR-181); without the floorplan it missed by 2.1 ns. Release builds leave out the uncore's development-only blocks (DR-180, 1.8K LUTs a chip). The full product chip (2026-10-22) places at 97.2% and routes with congestion-spreading placement, the uncore's 200 MHz-era slices off (DR-186) and the interrupt lines registered. The area pass is on main (10-22): rename's unread payload in LUTRAM (DR-185, about 2.9K fewer flip-flops a chip), the issue queues' readiness on carry chains (474 LUTs a chip), and memory protection (PMP) checked once per page when a TLB entry fills (DR-183, about 2K LUTs a chip, behind a switch, 0.17–0.19% of the boot's cycles). **The near-final product chip closed 100 MHz on 10-22**, in one of two placements: WNS +0.257 ns with no failing endpoint, the other placement 0.72 ns short. It's a preview with the last timing fixes before they reach main; a four-hart board image at 100 MHz is made from it (DR-188). The second thread costs about 6.5K LUTs a core, mostly duplicated control logic. Every area trick that costs cycles has a switch for a bigger chip, except two documented ones ([docs/spec/area_switches.md](docs/spec/area_switches.md)). Test modes run the one thread as thread 1, in its own half, and with phantom flushes of the idle thread, so the per-thread paths are exercised before a second thread runs. The checks for two threads are ready: the RVWMO litmus suite and a pair runner for the throughput target (two programs at once against one alone, at 30, 120 and 250 cycles of memory latency; since DR-184 the target is step 7's measured result, with no pair hanging and no loss for one program alone).
  - **M7 is complete (2026-10-23).**
  - **The litmus suite:** every test passes with no outcome the memory model forbids, at three memory latencies: 3,504 of 3,504 on all four harts, and 1,716 of 1,716 on one core's two threads.
  - **The two fixes behind it**, both found by the four-hart litmus run:
    - two loads of one address could see a newer and then an older value (CoRR);
    - an instruction-cache refill during a FENCE.I sweep could lose its writes.
  - **The throughput target is met:** 1.226 / 1.217 / 1.192× one thread at 30 / 120 / 250 cycles.

  - **The release image rc3_u095r:** WNS +0.748 ns, 112,806 LUTs (96.3% of the XCK26), built from main's design (tag m8-release-rc3).

- **M9 (hardening, the v1 release):** the scope was approved on 2026-10-23 (DR-190, [the M9 plan](docs/spec/m9-plan.md)).
  - **First:** the hardening that costs no LUTs and the v1 documentation. The trigger CSRs are done (2026-10-23).
  - **Before the new RTL:** structural fixes for the timing paths that keep failing at 96% fill (DR-191), so the chip closes 100 MHz reliably.
  - **Then:**
    - Performance counters with overflow interrupts (Sscofpmf), so `perf record` works on the board. On main since 2026-10-23, off by default (`TG_HPM`; about 870 LUTs a chip when on).
    - A 256-entry indirect-jump predictor, estimated at +2.4–2.9% of the two-hart Linux boot's busy cycles.
    - A 16-entry load-wait table, added by the user.
    - A JTAG debug module for OpenOCD and GDB, in development builds only.
  - **After v1:** uncached page mappings, cache-block instructions, misaligned accesses in hardware and store sets. Debian on this board gains little from them, and the release chip is at 96.3% of its LUTs.
- **Debian 13 on the board (DR-147, M5's exit, stage C):** on 2026-10-17 Debian 13.7 booted on two Tanager cores on the KV260. The chain is OpenSBI, U-Boot, then Debian's own riscv64 kernel package (6.12, SMP) from a virtio disk served by the A53, ending in systemd "running" with no failed units. The network works too: virtio-net bridged onto the LAN, DHCP, DNS, time and apt. Debian installs and runs its own software: gcc 14 from Debian's mirror builds programs on the RISC-V, and sysbench runs 2.03× faster on two cores than on one. Stage C's hardware and software are on main (5172c6a). On 2026-10-17 the same Debian ran at 100 MHz (two cores, build sc3_100), about 1.45× the 70 MHz results: login at 191 s, gcc and sysbench 1.3–1.45× faster. The RISC-V now boots Debian from its own SD partition (p3). Measured at 100 MHz: CoreMark 276.9 iterations/s per core and 547.2 for two cores at once, Dhrystone 140.6 DMIPS. Stage D is under way (below).
- **Two cores on the board (DR-150):** on 2026-10-17 two-core Linux booted on the KV260: two smt2 cores, harts 0 and 2, at 70 MHz. OpenSBI sees 2 harts, and Linux brings up 2 CPUs with SMP working (parallel runs, IPIs both ways). The two-core run also passes FPGA lockstep: all 408 million instructions from reset to power-off matched Spike, and again (396 million) on the normal device tree with the timer frozen during trace stalls. The way there found a synthesis-only bug (a name used before its declaration became an undriven net in Vivado). Every Vivado flow now fails on that class.
- **The board as a standard RISC-V SBC (DR-147):** stage C first: virtio storage, network and RNG served by the A53, then U-Boot and Debian 13 with its own kernel packages. Then stage D: the RISC-V drives the board's SD, Ethernet, USB and UART, and the A53 parks. Stage C runs on the board at 100 MHz. In stage D, D0 (probes), D1 (the RISC-V's window to the PS's peripherals), D2 (the fan regulated from the PL) and D3 (the RISC-V's own console on the PS's UART1) pass on the board. **D4 is met (2026-10-19, DR-172):** the board starts in one of two exclusive modes, chosen at boot from a record on the SD card. In ARM mode it is the A53's Ubuntu alone. In RISC-V mode the A53's boot firmware loads the Tanager bitstream, hands the SD card, UART1 and the fan to the RISC-V, and parks. Debian 13 then boots from the SD card through the PS's SD controller, with no software on the A53. Debian's reboot stays in RISC-V mode. `tanager-mode arm`, or a long break on the PMOD UART when the RISC-V hangs, returns the board to Ubuntu, and any missing or unconfirmed record falls back to ARM mode. **D5 is met (2026-10-19):** in RISC-V mode Debian drives the board's Gigabit Ethernet (the PS's GEM3) with its own drivers. It gets an address by DHCP, answers ping and SSH by name, copies files at about 2 MB/s (bounded by SSH's encryption on the 100 MHz cores), and runs `apt-get update` from Debian's mirrors. No FPGA change was needed, only the device tree and the A53's boot script. In RISC-V mode the board is now a networked, standalone RISC-V computer. USB is next.

  **A core race found by the board (2026-10-20, DR-176):** in RISC-V mode about one boot in 11 lost the SD card's interrupts, always around a boot or shutdown. A probe running from RAM caught it: the interrupt controller's source 21 had been claimed and never completed. The cause was in the core. When an interrupt arrived in the very cycle a device read went out, the read was cancelled and sent again after the interrupt. A claim read hands over the interrupt as it is read, so the first answer was lost. A directed test reproduces it, and the fix (the read waits for that one cycle) is on main. d4r2, d4r1's build with the fix, meets 100 MHz and ran 60 of 60 RISC-V-mode boots on the board without a loss (about 5 were expected at the old rate). Its 24-hour soak ran clean for 14.09 hours until a power cut ended it.
