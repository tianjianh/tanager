# Tanager

Tanager is a clean-room, 2-wide-decode, out-of-order RV64GC dual-core with two hardware threads per core (SMT2) that runs Linux on the AMD Kria KV260 (XCK26). Its IPC must beat NaxRiscv's, and it is built so 3-wide decode can be added next.

**Status.**
- **M1 (model and design-space exploration):** done. The parameter freeze was approved on 2026-10-13.
- **SMT2 model study:** done ([docs/perf/smt2_report.md](docs/perf/smt2_report.md)).
- **Roadmap:** single-thread bring-up (ST) → **v1, the first release: SMT2, 2-wide, 2 cores × 2 harts** (plan §6.5) → v2: 3-wide on the SMT2 core. All on the KV260 (plan §8.5).
- **Schedule (plan §11):** agent-built. Linux on the board about 4–6 weeks after M0 starts; v1 in about 3 months.
- **M0 (repository, CI, FPGA spikes):** done. Spike S1 ran on the board on 2026-10-14: an idle 64-byte DDR read from the FPGA takes 36.8 cycles (184 ns) at 200 MHz, and the two HP ports together move 6.35 GB/s. The spikes are reported in [docs/perf/spikes.md](docs/perf/spikes.md).
- **M2 (out-of-order core in simulation):** done on 2026-10-14. Lockstep passes in all four configurations; CoreMark 3.04 CM/MHz on the conservative M2 core.
- **M3 (Linux-capable core):** done in simulation on 2026-10-14. RV64GC, with F and D, runs in lockstep with Spike in all four configurations (ACT4 rv64imafdc 895/895), and Linux (OpenSBI, Buildroot lp64d) boots to userspace in Verilator. The area work toward v1's 103K-LUT bar continues as FPGA-native rewrites ([docs/perf/fpga_friendly.md](docs/perf/fpga_friendly.md)).
- **M4 (single core on the KV260):** in progress. The ARM side is up (stage A) and spike S1 is done. Stage B passed on 2026-10-14. First the traffic-generator bitstream: it loads with Linux's fan control, its memory path runs with 0 errors at native and at 250 injected cycles, and the RISC-V console comes out on the PMOD UART. Then **the real out-of-order core booted Linux on the board**: one `st` core at 60 MHz runs the SoC test program to PASS, and boots OpenSBI 1.9 and Linux 6.18 to a root shell and a clean poweroff, at native latency and at 250 injected read cycles, with the console on both the host bridge and the PMOD UART. **FPGA lockstep passed on 2026-10-14:** the A53 checked every one of the 335,786,888 commit records of a Linux boot to a root shell and poweroff against Spike, and none differed; at 250 injected read cycles too (355,612,637 records). **Next:** M4's last exit criterion, at least 100 MHz, which waits on the core's cross-unit timing paths.
- **Clock (DR-152):** v1's target is 100 MHz; 115 MHz was dropped for now on 2026-10-17, and a higher clock is taken only where it is cheap. Main meets 100 MHz on the board (sc3_100, +0.347 ns) and in the full chip with the second thread's area reserved (+1.065 ns). The user accepts a few MHz below 100 while M6's features go in (DR-162): with the return-address stack the full chip reaches about 95 MHz. With TAGE-lite as first built it reached only about 66 MHz, because one fetch stage chained 40–44 logic levels; with that stage restructured at no cycle cost (DR-165) and Vivado's ExploreArea optimisation (DR-166), the whole M6 set (the RAS, two-table TAGE, four misses, speculative wakeup) routes at 100 MHz with the second thread's area reserved: +0.725 ns, no failing path, 97.1% of the LUTs. The L1 data cache keeps 4 misses in flight by default (DR-156).
- **M6 (the core's performance features, DR-153):** started on 2026-10-17 alongside M5, measured in RTL simulation first. **The first M6 set is on main (aae0503, 2026-10-18):**
  - four L1D misses in flight (under Linux on the board, a 1 MiB memcpy −38% and /init 8% sooner);
  - speculative load wakeup;
  - a 32-entry return-address stack;
  - TAGE-lite with two tagged tables of 2K entries;
  - returns and straddling compressed instructions predicted at fetch, with a restructured fetch stage;
  - two rename fixes: a store's address no longer waits for its data, and ALU ops are steered with up-to-date queue room.

  CoreMark per MHz (rv64gc, timed regions, RTL simulation) went from 3.06 to 4.55 (flags A) and from 2.79 to 4.27 (B) over M6 so far, and Dhrystone from 1.48 to 3.08 DMIPS/MHz. The last merge alone makes the 20M-cycle Linux boot retire 14% more instructions. It costs about 2.1K LUTs per core, and the full chip still routes at 100 MHz with the second thread's area reserved.

  **Under Linux on the board (2026-10-19, two cores at 100 MHz, three boots):** CoreMark reaches 4.61 (A) and 4.36 (B) per MHz and Dhrystone 2.82 DMIPS/MHz, against 2.77, 2.29 and 1.41 before M6, and Linux reaches /init 21% sooner. Instructions per operation are unchanged, so the whole gain is IPC. The board found a micro-BTB bug that every simulation check had passed: two code blocks 2 MiB apart could share an entry, and decode no longer checked the shared target. It panicked Linux about 2.2 s into the boot. core-2's fix and a short directed test that reproduces it are on main. PMP with 8 entries (DR-167) saves about 2,970 LUTs a chip.

  **The final D4 bitstream (d4r1, 2026-10-19)** adds two M6 pieces aimed at Linux: the store ownership prefetch, where a store asks for write permission on its line as soon as its address is known, and FENCE.I by generation, which stops fetch waiting while the instruction cache is flushed. Against the build before them, page faults are 28% faster, 1 MiB memcpy 35% and memset 29% faster, and Linux reaches /init 10.5% sooner (0.83 s; 1.18 s before M6). CoreMark and Dhrystone are unchanged. Since then, an instruction-cache next-line prefetch (on main, d3e124a) fetches the following line on every miss, for 109 LUTs a core. In simulation, run the way the board runs, it brings /init a further 2.3% sooner.

  **Board time against simulation:** simulating the RTL the way the board runs predicts the board's boot phase by phase. It predicted d4r1's /init at 0.832 s before the board measured 0.831 s.
- **M7 (SMT2, the second thread in each core, DR-175):** started on 2026-10-19 on core-2's approved plan, eight steps, each behind a switch and merged with every cycle unchanged while the second thread is off. Step 1, thread ids through the pipeline, is on main (2026-10-20), with a test mode that runs the one thread as thread 1 so the per-thread paths are exercised early. The checks for two threads are ready: the RVWMO litmus suite and a pair runner for the throughput target (two programs at once must do at least 1.3× the work of one, at 30, 120 and 250 cycles of memory latency). The model predicts 1.27–1.31× once the second thread runs (step 5) and 1.33–1.35× with step 7's per-thread queue limits.
- **Debian 13 on the board (DR-147, M5's exit, stage C):** on 2026-10-17 Debian 13.7 booted on two Tanager cores on the KV260. The chain is OpenSBI, U-Boot, then Debian's own riscv64 kernel package (6.12, SMP) from a virtio disk served by the A53, ending in systemd "running" with no failed units. The network works too: virtio-net bridged onto the LAN, DHCP, DNS, time and apt. Debian installs and runs its own software: gcc 14 from Debian's mirror builds programs on the RISC-V, and sysbench runs 2.03× faster on two cores than on one. Stage C's hardware and software are on main (5172c6a). On 2026-10-17 the same Debian ran at 100 MHz (two cores, build sc3_100), about 1.45× the 70 MHz results: login at 191 s, gcc and sysbench 1.3–1.45× faster. The RISC-V now boots Debian from its own SD partition (p3). Measured at 100 MHz: CoreMark 276.9 iterations/s per core and 547.2 for two cores at once, Dhrystone 140.6 DMIPS. Stage D is under way (below).
- **Two cores on the board (DR-150):** on 2026-10-17 two-core Linux booted on the KV260: two smt2 cores, harts 0 and 2, at 70 MHz. OpenSBI sees 2 harts, and Linux brings up 2 CPUs with SMP working (parallel runs, IPIs both ways). The two-core run also passes FPGA lockstep: all 408 million instructions from reset to power-off matched Spike, and again (396 million) on the normal device tree with the timer frozen during trace stalls. The way there found a synthesis-only bug (a name used before its declaration became an undriven net in Vivado). Every Vivado flow now fails on that class.
- **The board as a standard RISC-V SBC (DR-147):** stage C first: virtio storage, network and RNG served by the A53, then U-Boot and Debian 13 with its own kernel packages. Then stage D: the RISC-V drives the board's SD, Ethernet, USB and UART, and the A53 parks. Stage C runs on the board at 100 MHz. In stage D, D0 (probes), D1 (the RISC-V's window to the PS's peripherals), D2 (the fan regulated from the PL) and D3 (the RISC-V's own console on the PS's UART1) pass on the board. **D4 is met (2026-10-19, DR-172):** the board starts in one of two exclusive modes, chosen at boot from a record on the SD card. In ARM mode it is the A53's Ubuntu alone. In RISC-V mode the A53's boot firmware loads the Tanager bitstream, hands the SD card, UART1 and the fan to the RISC-V, and parks. Debian 13 then boots from the SD card through the PS's SD controller, with no software on the A53. Debian's reboot stays in RISC-V mode. `tanager-mode arm`, or a long break on the PMOD UART when the RISC-V hangs, returns the board to Ubuntu, and any missing or unconfirmed record falls back to ARM mode. **D5 is met (2026-10-19):** in RISC-V mode Debian drives the board's Gigabit Ethernet (the PS's GEM3) with its own drivers. It gets an address by DHCP, answers ping and SSH by name, copies files at about 2 MB/s (bounded by SSH's encryption on the 100 MHz cores), and runs `apt-get update` from Debian's mirrors. No FPGA change was needed, only the device tree and the A53's boot script. In RISC-V mode the board is now a networked, standalone RISC-V computer. USB is next.

  **A core race found by the board (2026-10-20, DR-176):** in RISC-V mode about one boot in 11 lost the SD card's interrupts, always around a boot or shutdown. A probe running from RAM caught it: the interrupt controller's source 21 had been claimed and never completed. The cause was in the core. When an interrupt arrived in the very cycle a device read went out, the read was cancelled and sent again after the interrupt. A claim read hands over the interrupt as it is read, so the first answer was lost. A directed test reproduces it, and the fix (the read waits for that one cycle) is on main. d4r2, d4r1's build with the fix, meets 100 MHz and is being checked over 60 boots on the board.
